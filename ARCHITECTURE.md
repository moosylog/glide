# GLIDE Architecture & Modularization Plan

**Status:** Proposed
**Scope:** Directory layout and module separation strategy for migrating GLIDE from a single-file HTML app to a GitHub-hosted, buildable project — without a big-bang rewrite, and with the roadmap (touchpads, workspace/theme UX, visual combo editor, macro builder, capabilities marketplace) designed in from day one rather than bolted on later.

---

## 1. Why modularize now

GLIDE today is one `<script type="text/babel">` block: ~30 `useState` hooks and every handler live inside a single `App` component, domain logic (ZMK binding parsing/synthesis, layer-index remapping, GC) is interleaved with JSX, and there's no test harness beyond ad-hoc scripts. That's the right way to *start* a single-file tool — it's exactly why iteration has been fast — but it's the wrong shape for:

- Adding five roadmap features without every one of them touching the same 2,000-line `App` function.
- Writing regression tests for the domain logic bugs that keep surfacing in exactly that logic (hold-tap synthesis, layer reindexing, GC eligibility) — these are pure functions today, but they're not *isolated*, so testing them means booting a browser-shaped environment around them.
- Letting the Capabilities Marketplace run third-party `jq` transforms without those transforms having incidental access to the rest of the app.

## 2. Guiding principles

1. **Domain logic has zero UI dependencies.** Everything that knows what a `&kp` binding, a hold-tap, or a layer index *is* lives in `core/` and `schemas/`, and never imports from `ui/` or React. This is the single most important rule — it's what makes the domain logic unit-testable in milliseconds instead of requiring a rendered component tree, and it's what stops UI experiments from accidentally changing correctness-critical behavior.
2. **State is not UI.** Component tree shape can change (and will, five times over, for the roadmap) without touching how the layout config is stored, undone, or garbage-collected.
3. **Schemas are the shared contract.** The MoErgo JSON layout format is the thing every other module ultimately agrees on. It's defined once, typed once, and every boundary (file load, export, capability injection) validates against it.
4. **Extensions are a guest, not a member of the family.** Marketplace capabilities run through a narrow, sandboxed API — they get a JSON snapshot in and a JSON snapshot out, never a reference into live app state.
5. **Dependencies point one way:** `ui → state → core/schemas`. `io` and `extensions` depend on `core/schemas` but not on `ui` or `state` directly (they're called *by* state, or by top-level orchestration). Nothing in `core/` or `schemas/` imports anything above it. A lint rule (see §6) enforces this so it doesn't erode over time.

## 4. Module responsibilities at a glance

| Module | Owns | Never touches |
|---|---|---|
| `core/` | What a binding *is*, how it decomposes/recomposes, GC, layer remapping | React, DOM, `fetch`, `localStorage` |
| `schemas/` | What a layout JSON *looks like*, validation | Any behavior/logic |
| `io/` | Getting bytes in and out (files, gists, future firmware targets) | UI rendering |
| `extensions/` | Running third-party transforms safely | Direct mutation of `state/` — it hands back JSON, `state/` decides what to do with it |
| `state/` | *When* things change, undo/redo, persistence | How things look |
| `ui/` | How things look and how the user's hands map to `state/` actions | ZMK semantics — a component should never need to know what `&ht_auto_` collapse rules are |

## 5. Roadmap fit

The point of this layout is that none of the five roadmap items require restructuring — each has an obvious, already-provisioned home.

**Touchpad Configuration — a first, lighter slice landed early; the full item described here is still ahead.** This section originally scoped touchpads as a geometry problem: pointer *regions* rather than key indices, needing their own `core/geometry/touchpad.ts` and a `KeyboardCanvas.tsx` rendering branch for gesture zones. That's still real future work if GLIDE ever needs to model an actual touch-sensing surface (drawing zones, gesture mapping). But the immediately actionable, immediately requested need turned out to be smaller and didn't need any of that: Go60's two Cirque trackpads already exist as ordinary (if inert) key positions in the current geometry model (60/61, the round keys), and what MoErgo's own config UI actually edits for them isn't geometry at all — it's a ZMK *input-processor chain* (sensitivity scaling, axis flip/swap, movement-vs-scroll mode, per-layer overrides), pure firmware config with no rendering surface of its own. `core/zmk/inputProcessors.js` (parse/build over `config.inputListeners`, same shape as `core/behaviors/compile.js`) plus a `TouchpadSettingsModal` opened from the existing touchpad key positions covers that need entirely, without touching geometry, `schemas/`, or `KeyboardCanvas.tsx` at all — see the "Touchpad Settings" note in `README.md` for the full design, including why the JSON encoding for this corner of the format needed verifying against a real export rather than assuming it matched an ordinary key binding.

**UI & Workspace Enhancements.** This is what `state/workspaceStore.ts` and `ui/theme/` are for. Full multi-file workflows (several layouts open at once, each in its own tab) are still a workspace-level concern sitting above `layoutStore` — a workspace holds N layouts, each with its own dirty flag and undo stack; today's single-`config` model becomes one entry in that collection. But the *single*-layout slice of "unsaved changes" has landed early, out of real necessity rather than the full roadmap item: `glide.html`'s `isDirty` state, set on every edit and cleared by an Export or a fresh load, plus a `beforeunload` warning and a `guardUnsavedChanges` confirmation before any action that would discard it (see the "File handling" note below §5's Flows Automations one). That's the same *concept* the eventual `workspaceStore` needs per-layout, just not yet generalized to N simultaneous layouts — moving it there later is extending its scope, not redesigning it. Theme support replaces the current three hardcoded CSS classes (`oled`/`dark`/light) with a token system in `ui/theme/themes.ts`, with "custom theme" being a user-authored token set stored in `uiPreferencesStore`.

**Visual Combo Editor.** Mostly UI composition over logic that already exists: `core/zmk/combo.ts` already owns combo binding/keyPositions logic, and — nice existing asset — `MiniKeyboardMap.tsx` was already built generically enough (it's currently used for hold-trigger-key picking) to be reused as the combo mini-preview with zero changes. "Layer awareness" is just the combo editor reading the layer list out of `layoutStore` the same way `LayerList.tsx` does. The new surface area is entirely in `ui/inspector/comboEditor/` — an editor experience, not new domain logic.

**Macro Builder & Editor — landed.** This turned out to be the one roadmap item needing genuinely new *core* logic, not just new UI, exactly as anticipated below: `core/zmk/macro.js` (parse/build over `config.macros`' `bindings` arrays — `&macro_tap`/`_press`/`_release`, `&macro_pause_for_release`, `&macro_wait_time`/`_tap_time`, the four `&macro_param_<n>to<n>` forwarding controls — plus the CRUD/reference-safety helpers a rename/delete needs), symmetric with `core/behaviors/compile.js`. Grounded against 91 real macros across both real fixtures (tynstar, engrammer) rather than guessed — engrammer's real HRM macros and macro-invoking-macro pattern (`&mod_tab_chord_v2_TKZ` invoking `&mod_tab_v1_TKZ` as a step) turned out to already exercise every control behavior except two (`&macro_wait_time`/`_tap_time`, confirmed from ZMK's own docs instead). One thing the original scoping note below didn't anticipate: renaming/deleting a macro needed a *fuller* reference scan than the existing `core/usage.js`'s `countBehaviorUsage` (which only walks `layers`+`combos`, missing a macro named from a hold-tap's/tap-dance's own `bindings` list or invoked as a step inside a different macro) — `findMacroReferences` in the new module covers all three. The visual builder shipped as a third left-nav tab (`glide.html`'s `MacroBuilderModal`, opened from a **Macros** list beside Layers/Combos) reusing the *existing* key-assignment palette data (`PALETTE_DATA`/`searchAcrossAllPalette`) for behavior steps rather than a second keycode picker. Step reordering shipped as plain up/down buttons rather than the drag-and-drop this note originally anticipated (extending the layer-reorder pointer-drag pattern, or a library like `@dnd-kit`) — a macro's steps are typically a short, linear sequence, so buttons cover the real editing pattern without a second drag implementation; that remains available to add later if real usage shows a need for it.

**Sticky Key Builder & Editor — landed, not part of the original five roadmap items above, added as a direct follow-on to Macro Builder.** Once Macro Builder closed the "list-only, no editor" gap for macros, sticky keys (`&sk` behaviors, `config.stickyKeys`) were the one other behavior family left in exactly the same state — assignable by name from the ordinary key palette, with no way to create or edit one. `core/zmk/stickyKey.js` is a much smaller module than `macro.js`, by nature of the behavior it models: no ordered step sequence, just four flat properties (`releaseAfterMs`/`quickRelease`/`lazy`/`ignoreModifiers`, grounded against ZMK's own docs — zmk.dev/docs/keymaps/behaviors/sticky-key — since only one real sticky key exists across both real fixtures, engrammer's `&sticky_key_quickrel_v1_TKZ`). It reuses the exact same shape and conventions macro.js established: absence-vs-explicit-value preserved for all four properties (same reasoning as macros' `tapMs`/`waitMs`), and a `findStickyKeyReferences`/`renameStickyKey`/`deleteStickyKey` reference-safety layer copied structurally from `findMacroReferences` — which turned out not to be over-engineering for a single-example behavior: writing its test against the real fixture surfaced a genuine cross-reference neither module's author had gone looking for, engrammer's own `&sticky_key_quickrel_v1_TKZ` is invoked as a step inside a *different* real macro (`&sticky_key_oneshot_v1_TKZ`), exactly the kind of reference `core/usage.js`'s `countBehaviorUsage` would silently miss. One real divergence from macro.js worth noting: a sticky key's `bindings` field is not a binding-object array like a macro's — it's a plain array of behavior-name strings (`["&kp"]`) declaring what single-param behavior the sticky key wraps, confirmed against the real fixture rather than assumed to match macros' shape. The builder shipped as its own left-nav tab (`glide.html`'s `StickyKeyBuilderModal`, opened from a **Sticky** list; originally beside Layers/Combos/Macros, later moved under the collapsible Behavior Library section — see below) rather than folded into the Macros tab, keeping each behavior family's list independently searchable — the same reasoning that kept Macros its own tab rather than merging into Combos.

**Mod-Morph Builder & Editor — landed, the third and best-evidenced of the follow-on behavior builders.** Same gap again, this time for `&mod_morph` behaviors (`config.modMorphs`), and the most real-world-grounded of the three: 27 real, user-authored mod-morphs exist across both real fixtures (21 in tynstar, 6 in engrammer) — more than sticky keys' single example, and every one of tynstar's 21 turned out to be directly key-bound (found while writing `findModMorphReferences`'s tests, the same way macro/sticky-key reference-finding turned up real surprises). `core/zmk/modMorph.js` is structurally the smallest of the three, and deliberately so: unlike `macro.js`/`stickyKey.js`, it skips the parse/build translation layer entirely, because a mod-morph's real JSON shape (`{ name, description, cases: [{ binding, mods, keepMods }, ...] }`, confirmed against ZMK's own docs — zmk.dev/docs/keymaps/behaviors/mod-morph — and both real fixtures) is already the friendly model a settings UI wants, one-to-one; introducing a second representation would have been indirection with no round-trip risk to guard against. What it keeps from the established pattern is the CRUD/reference-safety layer (`findModMorphReferences`/`renameModMorph`/`deleteModMorph`/`cloneModMorph`/`uniqueModMorphName`), copied structurally from `findStickyKeyReferences`, since a mod-morph's name can be referenced from the identical set of places. One real invariant `normalizeModMorphCases` encodes, found by reading real data rather than assumed: case 0 (the default) always has empty `mods`/`keepMods` in every real example — not a UI choice, but inherent to what "default" means when `&mod_morph` itself only ever tests one `mods` bitmask (for case 1). The builder shipped as its own left-nav tab (`ModMorphBuilderModal`, **Morphs**; originally beside Layers/Combos/Macros/Sticky, later moved under Behavior Library), reusing the Macro Builder's palette-based binding-picker UI for both of a mod-morph's fixed two cases (no step list needed, since the case count is fixed at exactly two) and a full 8-flag mods/keep-mods toggle grid — sized to the real variety found (tynstar's `&parsl`/`&parsr` each trigger on only one side's Shift, with a real non-empty `keepMods`), not just the common both-Shift case this module's author expected going in.

**Hold-Tap Builder and Tap-Dance Builder — landed, closing out the named-behavior-builder set at five.** The same gap a fourth and fifth time, for `&hold-tap` (`config.holdTaps`) and `&tap-dance` (`config.tapDances`) behaviors — the two ZMK considers core enough that `core/slots.js` already auto-generates GLIDE-owned instances of both (`GLD_ht_`/`GLD_td_`-prefixed, decomposed into the key inspector's Hold/Double-Tap slots), but with no editor for a *named, user-authored* one beyond the gear-icon panel's mods-only mod-morph toggle. Hold-taps are, by a wide margin, the best-evidenced named behavior in either fixture: **36 real instances** (35 in engrammer alone — its entire home-row-mods layout is built from them — 1 in tynstar, `&strong`), dwarfing macros' 91-combined lead only because macros are steps-heavy where hold-taps are one-per-key. Tap-dances are the opposite extreme: zero real instances in either fixture, so `tapDance.js` and its test are grounded on the binding-object `bindings` shape `core/slots.js`'s own `buildBindingAndConfig` already synthesizes for GLIDE's auto-generated tap-dances (proven real by virtue of being this codebase's own synthesis logic), plus ZMK's docs, rather than a real top-level record — the module's own header comment says so explicitly rather than implying fixture grounding it doesn't have.

`core/zmk/holdTap.js` follows `modMorph.js`'s lead in skipping a parse/build layer, but reading all 36 real records settled two things ZMK's docs alone wouldn't have. First, `bindings` is a plain 2-element array of behavior-name **strings**, not binding objects with params — true of every real record and matching `core/slots.js`'s own `makeHoldTap`, unlike a mod-morph's or macro's binding-object `bindings`. Second, and more consequential: real records — engrammer's HRM ones specifically — carry a `holdTriggerKeyPositions` field, a per-key physical-position allowlist sometimes 40+ entries long, that this module has no UI-facing editor for. A naive `updateHoldTap` that rebuilt the record field-by-field from the form's managed fields would have silently deleted that array the first time anyone edited an HRM hold-tap's tapping term through the builder — real data loss, not a hypothetical one. `updateHoldTap` instead merges onto the existing record (`{ ...existing, ...managedFields }`), so any field the module doesn't manage survives untouched; this is now the pattern the other four modules' `updateX` functions notably *don't* follow (they rebuild from scratch), because none of their real fixture data ever exposed a field worth preserving this way — another case of a real invariant only surfacing because the test was written against real data rather than a synthetic record with only the fields the author thought to include.

`core/zmk/tapDance.js` is the more conventional of the two: an ordered `bindings` array of full binding objects (2+ required, matching ZMK's own minimum), plus a single `tappingTermMs`. Its `findTapDanceReferences` and `holdTap.js`'s `findHoldTapReferences` both extend the reference-safety scan one bucket further than `modMorph.js` did: they also check `stickyKeys[].bindings`, a bucket neither `stickyKey.js` nor `modMorph.js` had gotten around to yet — not because it was found broken, but because each successive module in this series has closed one more gap in the same scan rather than the earlier ones being retrofitted.

Both builders shipped as their own left-nav tabs (`HoldTapBuilderModal`/**Hold-Taps**, `TapDanceBuilderModal`/**Tap-Dances**) from the start under Behavior Library (see below) — by the time these two landed, a sixth and seventh top-level tab was no longer a defensible width, which is what prompted the nav restructure below rather than the other way around. The Hold-Tap modal uses plain text fields for its two behavior-name bindings (no params to pick, so `ModMorphBindingPicker`'s full palette search would be overkill); the Tap-Dance modal reuses `ModMorphBindingPicker` per tap instead, since tap-dance bindings genuinely are full binding objects, with an Add Tap / per-row-remove control enforcing the 2-tap floor.

**Behavior Library nav section — landed, a pure navigation restructure prompted by the five behavior builders above.** With Macros/Sticky/Morphs/Hold-Taps/Tap-Dances all shipped as top-level tabs, the sidebar had seven tabs for two very different audiences: Layers/Combos, which essentially everyone using GLIDE touches, and five behavior editors most people will open rarely if ever. Layers/Combos now stay the only always-visible row; the five behavior tabs moved under a collapsible **Behavior Library** section beneath it (`glide.html`'s `behaviorLibraryExpanded` state), collapsed by default on every fresh mount. The section also auto-expands whenever `leftNavMode` is already one of its own five values (`BEHAVIOR_LIBRARY_NAV_MODES`) — e.g. if a prior session/re-render left `leftNavMode` pointing at `'StickyKeys'` — so collapsing the section can never strand the active view on a hidden panel; this check is `||`'d with the explicit toggle state rather than replacing it, so a user-triggered collapse still works once they navigate to Layers. Being a pure UI reorganization, it touched none of the five `core/zmk/*.js` modules or their CRUD contracts — only `glide.html`'s sidebar JSX and the `open*Tab()` test helpers in `macroBuilder.test.js`/`stickyKeyBuilder.test.js`/`modMorphBuilder.test.js`, which now click the section open first if its tabs aren't already visible (mirroring what a real user has to do post-restructure). Shipped initially as "Advanced Behaviors," then renamed to **Behavior Library** the same day after the project owner caught a real naming collision: GLIDE already has an unrelated per-key inspector tab titled "Advanced Behaviors" (`activeVerticalTab === 'Advanced'`, a search-and-*assign* picker over existing behaviors for the selected key, pre-dating this session). Two different features — one assigns an existing behavior to a key, the other creates/edits the behavior definitions — sharing one label was genuinely confusing, not a false alarm, so the fix was a rename rather than a "these are actually fine" explanation: `BEHAVIOR_LIBRARY_NAV_MODES`/`behaviorLibraryExpanded` in `glide.html`, and `behaviorLibraryNav.test.js` (replacing `advancedBehaviorsNav.test.js`) which now also asserts the two never collide.

**Canvas pointer-capture bug — fixed, pre-existing, unrelated to the Behavior Library work above.** Reported the same session as "plus and minus to resize the keyboard on the canvas seem broken," and confirmed: they were. `KeyboardContainer`'s `handlePointerDown` (the handler behind the canvas's click-and-drag panning) calls `e.currentTarget.setPointerCapture(e.pointerId)` on `pointerdown` for anything not matching `e.target.closest('.p-key')` — meaning any pointerdown that isn't on a key tile is assumed to be the start of a pan gesture. That's wrong for the zoom +/- controls, the Paste button, the Clear Clipboard button, and Focus Mode's "Done Editing" button, all real `<button>` elements floating inside the same `canvas-container` the pan handler is attached to. Once the canvas captures the pointer, the browser retargets the matching `pointerup`/`click` away from the button to the capturing element, so the button's own `onClick` — the thing that actually calls `setScale`/etc. — never fires; the click is silently swallowed. Fix was a one-line addition to the existing exclusion: `e.target.closest('.p-key') || e.target.closest('button')`, mirroring how key tiles were already excluded. Two things made this bug easy to miss and, initially, hard to verify: (1) it produces no error and no visual feedback — the button just looks unresponsive, easy to mistake for a debounce or a slow re-render rather than a swallowed event; (2) jsdom's `getBoundingClientRect`/pointer-event stubs don't reproduce real pointer-capture retargeting, so `tests/ui/`'s existing jsdom-based suite — including the zoom-percentage assertions already covering these buttons — passed both before and after the fix and would never have caught it either way. Confirming this required a real browser: a Playwright/Chromium session against an actual rendering of `glide.html` (not a stripped-down script-injection harness — an early attempt at one produced a bogus off-viewport button position and misleading results, discarded once traced to the harness itself lacking the app's real CSS) showed the zoom percentage frozen across 6 real clicks before the fix, and moving symmetrically (81%→89%→97%→105%→97%→89%→81%) after it. No `core/*.js` module or test file changed — this was contained entirely to one exclusion check inside `glide.html`'s `KeyboardContainer`.

**Non-technical-audience UX pass — three targeted fixes from a design review, landed together.** Same review that produced the "Advanced Behaviors" vs. "Behavior Library" rename above, aimed at a stated goal: GLIDE competing on usability specifically, for consumers with no ZMK background, not just power users.

- **Slot-link order/size.** `SLOT_LINK_LABELS`'s four "also specify" links, and the matching `activeSlotKeys` push order once a slot is actually added, were reordered from `shiftTap, hold, doubleTap, label` to `hold, doubleTap, label, shiftTap` — ranked by how common/approachable each is for someone without ZMK background rather than by build history (shiftTap/Shift Action shipped first historically, which is the only reason it used to lead). Hold actions (dual-purpose/home-row-mod keys) are the most common "extra" a real layout uses; a custom label needs no ZMK knowledge; Shift Action is the most advanced of the four (a mod-morph under the hood), so it's last. The hint text itself also moved from `text-[11.5px]` to `text-[12.5px]` — legible as a real feature list, not fine print. `keyEditorSlotOrder.test.js` covers order and size.
- **"Switch Layer" rename.** A second naming collision, same species as Advanced Behaviors/Behavior Library, found while investigating the first one: the per-key vertical tab that assigns a layer-*switching* action (Momentary/Layer-Tap/Sticky/Toggle/Switch-To — `activeVerticalTab === 'Layer'`) was titled "Layers," identical to the left sidebar's own "Layers" toggle (which manages/reorders the layers themselves — a different job entirely). Renamed the per-key tab's `title` to **Switch Layer**; no behavior changed, only the label. `switchLayerTab.test.js` proves the rename and that `layerTap.test.js` (which drives this tab by title) still works under the new name.
- **Lighting: Paint Mode, plus a sticky-tab fix that benefits every per-key tab, not just Lighting.** Two compounding causes made coloring more than one key tedious: `handleCanvasKeySelect` forced `activeVerticalTab` back to `'Keymap'` on every canvas key selection (so picking a color, then clicking the next key, silently bounced you off Lighting every single time), and even without that, coloring was strictly one-key-at-a-time (select → click swatch). Fix 1: `handleCanvasKeySelect` no longer force-switches tabs at all — whichever tab is open when a different key is selected stays open. This is a general fix, not Lighting-specific: it equally lets Advanced Behaviors or Switch Layer stay open while assigning the same behavior/layer action to a run of keys. Fix 2: a real **Paint Mode** in the Lighting tab. `paintColor` (new state, `undefined` until a swatch is first clicked — including the "off" swatch, which arms the real value `null`, the eraser) tracks whichever color was picked most recently, independent of any one key's own decoration; the currently-armed swatch gets a ring (`ring-2 ring-app-accent`) so it's visible which color is loaded. Turning Paint Mode on and then clicking or click-dragging across keys on the canvas colors every key touched, via `applyPaintColorToKey`, without needing to select each one first. The interesting part is how the whole drag stroke becomes ONE undo step rather than one per key: `applyPaintColorToKey` writes straight into `config` via `setConfig`'s functional form (skipping `pushHistory` entirely) for every key painted during the stroke, capturing the pre-stroke snapshot into a ref (`paintStrokeBaseRef`) the first time a key is painted; `commitPaintStroke`, fired from the same `pointerup`/`pointercancel` handlers `KeyboardContainer`'s existing drag-to-swap gesture already uses (paint mode replaces that gesture's swap behavior with paint behavior for the duration of the stroke, reusing its `document.elementFromPoint`-based hit-testing to find which key the pointer is currently over), then pushes that one ref value onto `undoStack` and runs the same `runGC` pass every other edit goes through. Paint Mode's actual effect on the canvas is gated by `paintMode && activeVerticalTab === 'Lighting'` at the `<KeyboardContainer>` call site — not by a `useEffect` that force-disables the toggle — so switching tabs away stops painting immediately, and switching back to Lighting resumes it without needing to re-arm anything. `paintMode.test.js` covers the disabled-until-armed toggle, single-click paint, a two-key drag landing as one undo step, the tab-switch cutoff, and the sticky-tab fix across Lighting/Switch Layer/Advanced Behaviors.

**Flows Automations (formerly "Capabilities Marketplace") — landed early, in a deliberately smaller shape than originally envisioned here, then corrected twice after real use.** `core/capabilities/{paramBinding,catalogSchema,jqRunner,applyFlow,builtinCatalog}.js` (plain JS, same pattern as `core/io/`) is the actual v1: browse a catalog and *apply* an automation directly — no `capabilityRegistry.ts`, no `extensions/` top-level folder, no install/uninstall lifecycle or persisted state beyond the last run's result. That's a deliberate scope cut (confirmed with the project owner): an automation (internally, a "Flow") is a one-shot jq mutation, not something with a lifecycle to manage, matching how Flows4JSON's own app already treats them. `applyFlow.js` runs an automation's jq transform (`jqRunner.js`, against a plain JSON snapshot of the config — no live references) and hands the result to the *existing* `loadLayoutObject` (this repo's `schemas/validate.ts` equivalent) before it's allowed anywhere near React state; a passing result then goes through the *same* `runGC` every other edit does. The "bundles can be literal `.flows` artifacts" synergy this section hoped for turned out to be exactly true, confirmed by reading the real `moosylog/flows4json` repo: `buildScriptWithParams` replicates that app's own `getScriptWithParams` param-binding algorithm byte-for-byte. A second, less obvious replication turned out to matter just as much: Flows4JSON's own app runs every uploaded file through a "normalizer prologue" before any flow ever executes, synthesizing a `.layout.keys` positional structure real MoErgo exports never have (some real automations — the Home-Row Mods family — read it directly). `applyFlow.js` now runs that exact prologue too, discovered only after a real user hit jq's own unhelpful "Cannot iterate over null (null)" — a reminder that "copy the param-binding algorithm" wasn't the whole portability contract; the input-normalization step was just as load-bearing and much easier to miss by reading the *scripts* rather than the app's upload handler.

The catalog itself was the second correction: v1 fetched `catalog.json` live from `moosylog.github.io` at runtime. Feedback was that these should be "part of GLIDE," not pointing at an external site — so `builtinCatalog.js` now bundles the catalog directly in the repo, each entry run for real against a real layout before being added, with a regression test (`tests/core/capabilities.test.js`'s `builtinCatalog` suite) that re-runs all of them on every test pass, and that also pins the exact set of uids expected so a silent addition or regression doesn't slip by unnoticed. First pass bundled 6 of upstream's real automations (one per category that existed then, individually verified rather than nominally porting everything); a second pass, believing the *live site's* `catalog.json` (12 entries) was the full upstream catalog, added the remaining 4 to bring the bundled set to 10. That assumption was wrong, and a real user caught it: the live site lags the **repo's own** `catalog.json` (`github.com/moosylog/flows4json`), which actually lists 38 entries. The third pass re-sourced from the repo directly and bundled every real mutator in it — 32, once six are excluded for cause, not for scope: five launcher cards (`colors_launch_kiilix`, `l_cleaner`, `l_hrm_tuner`, `l_oryx_swap`, `l_qwerty_swap` — no script, just an `appUrl`) and `hrm_bil_dynamic`, which upstream's own `catalog.json` files under a `category` of `"Test"` with a `script` that's verifiably truncated mid-expression — it fails to even compile, which reads as an unfinished publish upstream, not something to patch around here. That pass also caught a real upstream data bug (two entries both literally uid'd `se_symbol`, one Windows/Linux, one macOS — disambiguated here as `se_symbol_mac`) and a second instance of the same Go60-geometry conflict already found in `colors_createRGBscheme` (`mirror_keyboard_halves` hard-codes the identical exact-60-keys check), both scoped to `glove80`-only rather than shipped silently broken on Go60. Bundling still trades a live-fetched catalog's free upstream-tracking for GLIDE-side work validating each addition by hand — judged non-negotiable once the alternative is shipping unverified scripts, especially given how easy it turned out to be to under-count upstream's own catalog by relying on its deployed mirror instead of its source. The format gained one field with no upstream equivalent, `successMessage` — hand-written per entry, shown only on an actually-successful apply.

**Third correction: `builtinCatalog.js` was itself replaced by individual `.flows` files, so a Flow can change without touching any JS.** Bundling fixed "part of GLIDE, not an external site," but a single 1,000+-line JS array still meant every new or edited automation was a diff to `core/capabilities/builtinCatalog.js` — exactly the "touch the core app to add a flow" friction the project owner then asked to remove. The catalog now lives as one `.flows` file per automation (same TOML-ish format `flows4json` itself uses — `uid`/`title`/`description`/`script`/`[manifest]`/`[[param]]` — plus the GLIDE-only `successMessage` field) under `flows/shared/`, `flows/glove80/`, or `flows/go60/`, filed by which keyboard(s) it actually supports rather than all living in one flat directory. `scripts/buildFlowsIndex.mjs` (run via `npm run build:flows`, and auto-committed by `.github/workflows/sync-flows-index.yml` on any push touching `flows/**`, mirroring `sync-pages.yml`'s pattern for `index.html`) compiles every `.flows` file into `flows/index.json` — the flat array `catalogSchema.js`'s `parseCatalog` already expected, unchanged. `glide.html` now `fetch()`es `flows/index.json` at startup (same-origin, not third-party) instead of importing a bundled array, with a `flowsCatalogStatus` loading/error state shown in `CapabilitiesModal`. `core/capabilities/builtinCatalog.js` is gone entirely; `buildFlowsIndex.mjs` itself enforces the shared/glove80/go60 split by refusing to build if a `.flows` file's folder disagrees with its own `manifest.keyboards`.

**UI placement and browsing, corrected three times after real use.** The automations browser first shipped as a third tab beside Layers/Combos in the left nav. That was a mistake worth recording: Layers and Combos are editing *modes* — surfaces you keep flipping between for the length of an editing session — while an automation is a one-shot, occasional action, closer in kind to Export than to Combos. It now opens as a modal from a toolbar button, matching `ui/inspector/` in spirit for the eventual `ui/` decomposition: an automation's browse/detail/apply UI is an *overlay* over the editing surface, not a fourth thing living inside it. The second correction was to browsing itself: a flat, scrolling list of every automation got harder to navigate as the catalog grew, so the modal's home screen is now an app-store-style grid of category tiles — icon, a small preview strip of that category's own automation icons, name, count — drilling into a category's own list and then an automation's detail view; a search box skips both levels and matches across all categories. Every list row and detail view also shows a short hardware badge (`flowHardwareLabel` in `ui/modals.js`: "Shared", "Go60", "Glove80" — matching the `flows/shared|go60|glove80/` folder names, not "Go60 only"/"Glove80 only" wording) so compatibility is visible while scanning, and doubles as a pointer to where that flow's own `.flows` file actually lives. And after a run, what used to be a shared "Recent Activity" log is now a small result box scoped to that one automation's own detail view — success plus its custom `successMessage`, or the real jq error — since the ask was specifically for a result *of that run*, not a feed of every run.

The third correction, once the catalog grew to 32 entries across nine categories: showing an incompatible automation at all — dimmed, with a disabled Apply button and a "Not compatible with this keyboard" banner — stopped being the right call. A real request was explicit about it: a Go60 owner should only ever see Go60-compatible automations, a Glove80 owner only Glove80-compatible ones, full stop, not a browsable dead end. `glide.html` now filters the bundled catalog down to the current keyboard's compatible subset (`isFlowCompatible`, once per config change, before it's ever handed to `CapabilitiesModal`) rather than filtering inside the modal's render — which let the modal's own dimming/disabling logic be deleted outright instead of maintained alongside a second filtering mechanism. A category with zero automations for the loaded keyboard simply doesn't appear in the grid; search only ever surfaces automations that would actually work. External-app "launcher" catalog cards (empty `script`, an `appUrl` instead) are still dropped entirely at the `catalogSchema.js` parse boundary — GLIDE never opens a URL on the user's behalf as part of this feature, by design, not just by omission in the UI; not moot now that the full upstream catalog is bundled, since five real entries are exactly this case.

**Startup performance and file handling — both landed early, out of direct user feedback rather than the roadmap order above.** Neither needed new domain logic (unlike Macro Builder, say), so both were straightforward to do now rather than wait for a Vite-based Phase 0.

*Startup* used to load, for every visitor, with zero loading feedback while React/ReactDOM's development builds, Babel Standalone, the Tailwind CDN's in-browser JIT compiler, and jq-web's wasm engine all downloaded and (for Tailwind) recompiled at runtime, several blocking network round-trips deep, before anything painted. Fixed without a bundler: a plain-HTML/CSS splash screen in `glide.html`'s `<body>` (no React/Babel dependency, since it has to render before either has necessarily finished loading) now shows immediately and removes itself once the real UI has mounted; the three head `<script>` tags for React/ReactDOM/Babel are `defer`red so the browser can reach and paint that splash instead of blocking on those three round-trips first; React/ReactDOM point at their production builds instead of development ones; and — the largest single cut — the Tailwind CDN's runtime compiler is replaced by a static, pre-generated stylesheet (`core/styles/tailwind.generated.css`, built by `npm run build:css` from a real `tailwindcss@3` CLI + the same theme-extension object that used to be handed to the CDN's `tailwind.config = {...}`; see `core/styles/README.md`), and jq-web's wasm binary is no longer loaded upfront for everyone — `ensureJqEngineLoaded` in `glide.html` injects that one `<script src>` itself, lazily, the first time Flows Automations is actually opened. None of this needed Vite: a static-CSS build step and `defer`/lazy-`<script>` are within what a build-step-free single HTML file can already do: the Vite migration in §7 is still real, but for a much smaller, more targeted win than "startup is slow."

*File handling* was a real, reported gap, not a nice-to-have: once a layout was loaded, the "Load File"/template buttons that exist on the empty start screen simply had no equivalent afterward — the only path back to them was an unlabeled click on the sidebar's "GLIDE" logo, itself firing a native `window.confirm(...)` with no way to save first, and since there was no autosave, "unsaved changes" in that popup's text was *always* true. First fixed with a File menu hidden behind one icon button in a floating toolbar pill, the `isDirty`/`beforeunload`/`guardUnsavedChanges` mechanism described above §5's UI & Workspace Enhancements note, and one new small component, `ConfirmDialog`, replacing all four of the app's native `window.confirm()` call sites (detach-shared-behavior, delete-layer, clear-all-actions, and the discard-guard) with an in-app dialog that can offer a real third option — "Export First" — not just discard-or-cancel. `ConfirmDialog` and the underlying `isDirty` mechanism weren't touched again below; what needed a second pass was purely *where* file-level UI lived.

**Top bar and panel placement — corrected once, from direct UX feedback, right after the file-handling pass above shipped.** The floating icon-only File menu, plus an unsaved-changes dot living inside the Layers/Combos sidebar's own header, drew real criticism: file-level chrome was competing visually and structurally with the content panel it sat on top of, and a single icon hiding New/Import/Export was exactly the kind of undiscoverable menu Nielsen Norman Group's menu-design guidance warns against. Two decisions were made deliberately, not by default: (1) a persistent, full-width `<header>` now carries file identity (GLIDE mark, layout name, unsaved dot) on the left and labeled New/Import/Export plus Undo/Redo/Settings/Flows-Automations on the right — this is the *only* place any of that lives now, so the Layers/Combos sidebar's own header is gone and that `<aside>` is purely a content-editing surface; (2) rather than building true freeform dockable panels (the VS Code/Blender/Figma pattern — real flexibility, real learning curve, the wrong trade for a tool aimed at non-technical keyboard owners first), GLIDE gained one more **curated layout preset** alongside the existing `layoutMode` (bottom/right key inspector): `sidebarSide` (left/right for the Layers/Combos panel itself), same `localStorage`-persisted shape, exposed the same way in Settings. Both toggles are a CSS `order` swap on sibling flex children, not a rewrite — `sidebarSide` additionally mirrors the resize-handle side and drag-direction sign so resizing still feels correct with the panel on either side. The canvas-contextual floating pills (Zen-Mode/clipboard/hint top-center, zoom bottom-right) were deliberately left where they are: they describe the canvas itself, not file state, so the header redesign didn't touch them.

## 6. Tooling recommendations

- **Vite** for the dev server/bundler — fast, minimal config, and the plugin ecosystem matters once `jq-wasm` needs lazy-loading for the marketplace.
- **TypeScript, adopted incrementally, `schemas/` and `core/` first.** These are exactly the modules where this session's real bugs lived (an ambiguous `null` vs. object shape, a stale-state batching mistake) — the modules with the highest payoff from static typing. `ui/` can stay `.jsx` for longer if that's a smoother transition; `tsconfig.json` with `allowJs: true` supports mixing both during migration.
- **Vitest** for `core/`/`schemas/` unit tests — no DOM needed, matching principle #1.
- **Playwright** for `tests/e2e/`, replacing the ad-hoc jsdom harnesses used to find and confirm this session's fixes with a permanent, repeatable suite — the two real sample layouts become committed fixtures, and every bug found from here on gets a fixture-based regression test before it's marked fixed.
- **GitHub Actions**: `ci.yml` runs lint + typecheck + `vitest` + `playwright` + build on every PR; `deploy.yml` builds and publishes to GitHub Pages on merge, so "run this from GitHub" means both "clone and `npm run dev`" and "there's always a live deployed build at a Pages URL."
- **ESLint import-boundary rule** (e.g. `eslint-plugin-boundaries` or a custom rule): enforce that `core/` and `schemas/` cannot import from `ui/`, `state/`, or `extensions/`. This is the one guardrail worth automating rather than relying on code review, since it's exactly the kind of rule that erodes silently under deadline pressure otherwise.

## 7. Migration strategy (incremental, not big-bang)

The app works and is actively being tested against real files — the migration should never leave it in a broken state between phases.

1. **Phase 0 — scaffold.** Stand up the Vite + TS repo skeleton alongside the existing `glide.html`, wired to build to a single output bundle so deployment behavior doesn't change yet.
2. **Phase 1 — extract `core/`.** Pure functions, zero JSX, easiest to move and highest immediate value: write Vitest tests *first* using this session's known bug scenarios (empty-key Layer-Tap, Clear-All-Actions, the layer-reindexing fix, the naming convention) as the initial regression suite, then move the functions in behind those tests.
3. **Phase 2 — extract `schemas/` and `io/`.** Type the layout format, route file load/export through validation. Two self-contained slices of this have landed early, ahead of the rest of Phase 2:
   - `core/behaviors/{schemas,registry,compile}.js` — hold-tap/tap-dance settings became schema-driven (a `DynamicBehaviorForm` component renders any behavior's whole settings panel from a declarative property list, no per-property JSX), because it was the part of the UI accumulating the most one-off logic already.
   - `core/io/{layoutSchema,loadLayout,exportLayout}.js` — the top-level layout shape now has a real (permissive, not a strict allowlist — see the file header) validator, and `handleFileUpload`/`fetchTemplate`/`handleExport` in `glide.html` are thin DOM/network adapters over pure `parseLayoutJson`/`loadLayoutObject`/`serializeLayout` functions. This is what makes "plug into an API instead of a file picker" (see the roadmap items above) a matter of writing a new adapter later, not touching validation or serialization logic.

   Both are deliberately plain JS objects/functions rather than TOML or a TS+Zod-style schema — a format needing its own parser or a bundler would either add a dependency for no real benefit pre-Vite, or smuggle a toolchain migration in under a feature that didn't ask for one; plain JS loads like every other `core/*.js` module and stays Vitest-testable today.

   A third slice has also landed early, out of Phase 5's roadmap rather than Phase 2's, since it was the next feature requested: `core/capabilities/{paramBinding,catalogSchema,jqRunner,applyFlow,builtinCatalog}.js` — a v1 Flows Automations engine (browse/apply a GLIDE-bundled, individually-verified catalog; see §5's "Flows Automations" for the full design note, what was deliberately cut from it, and the two UI-placement corrections). It reuses `core/io/loadLayout.js`'s `loadLayoutObject` as its result validator and loads the real `jq-web` engine the same way Flows4JSON's own app does — tested against real `.flows` files with the real jq-web engine (not mocked), which is how a CRLF-mistokenization quirk, an error-message-stripping quirk, a missing `.layout.keys` normalizer step, and a Go60 key-count mismatch in one bundled entry were all actually found rather than assumed.
4. **Phase 3 — decompose `ui/`** component by component (start with the least-coupled: `MiniKeyboardMap`, then `Key`/`KeyboardCanvas`, then the inspector panels), keeping `App.tsx` as a thinning shell throughout rather than deleting it in one step.

   A first slice of this has landed early, in the same no-build-step spirit as the Phase 2 slices above: every component in `glide.html`'s single inline script that was already self-contained (no reach into `App`'s own state/handlers — just props and `window.GlideCore`) now lives in `ui/*.js` (`shared.js`, `canvas.js`, `sharedForms.js`, `modals.js`, `builders.js`; see `README.md`'s "Status" section for the full breakdown), each file an IIFE attaching its exports to a new `window.GlideUI` — exactly the `window.GlideCore` convention, one level up. `MiniKeyboardMap`/`KeyComponent`/`KeyboardContainer` (this phase's own suggested starting point) are the first three names in that list, in `ui/canvas.js`.

   A second slice, the custom-hooks half of this phase, has also landed: `ui/hooks.js` adds `useUndoHistory()` (`config`/`setConfig`/`undoStack`/`redoStack`/`isDirty`/`pushHistory`/`undo`/`redo`, previously three separate top-level declarations 250-400 lines apart inside `App`) and `usePersistedState()` (a generic `localStorage`-backed `useState`, replacing five near-identical hand-written pairs for theme/layout-mode/sidebar-side/OS-override/panel-width) to the same `window.GlideUI` namespace, same IIFE-plus-`Object.assign` convention as `ui/shared.js`. Every call site inside `App` that used these (around 50, for `pushHistory` alone) is unchanged — still the same variable/function names, now sourced from two hook calls near the top of `App` instead of scattered `useState`/`useCallback` declarations. What's deliberately still untouched at that point: `App`'s other ~25 `useState` hooks, its remaining handlers, and all of its JSX.

   A third slice — splitting `App`'s own `return (...)` JSX apart, the harder remainder above — is now under way, going least-coupled-first rather than as one pass, with the full test suite re-run after each individual extraction rather than batched at the end (see README.md's "Status" section for the reasoning and the planned order: Settings modal, then the top bar, then the left sidebar, then the key inspector panel last). `SettingsModal` (`ui/modals.js`) is the first one landed — purely presentational, since every value it touches was already a `usePersistedState` pair from the slice above. `TopBar` (`ui/topBar.js`) is the second — also purely presentational (props only), with its one piece of local state (`showNewMenu`) left as a plain `useState` in `App` and simply threaded through as a prop, since this step is about the JSX split specifically, not further hook extraction. `Sidebar` (`ui/sidebar.js`) is the third and biggest — the Layers/Combos/Behavior Library `<aside>`, around 70 props, still purely presentational. `InspectorPanel` (`ui/inspector.js`) is the fourth and final one, and the hardest: the per-key/per-combo `<aside>` beside the canvas — Combo Gear Settings plus the five-tab Keymap/Advanced Behaviors/Switch Layer/Lighting/JSON switcher — around 50 props. It's the one place this slice bent the "purely presentational, call site unchanged" rule: the original `{config && (<aside>...</aside>)}` gated the *entire* aside on `config` at `App`'s call site, unlike the header/sidebar (which always render their outer element and gate only inner content), so that gate moved inside `InspectorPanel`'s own return instead, letting `App` call it unconditionally like `<TopBar/>`/`<Sidebar/>`. It was kept as one component rather than split per-tab (a possibility floated when this slice was planned) because the tabs share too many closures over `App`'s state (`renderSlot`, `parsedSlots`, `assignAction`, `isItemActive`) for a multi-file split to reduce coupling rather than just relocate it. With this landed, the third slice's four-step plan is complete: `App`'s `return (...)` is down to its outer shell (`TopBar`, `Sidebar`, the canvas `<section>`, `InspectorPanel`, the modals) plus the hooks/handlers every piece still reads. Every slice here — this one and the custom-hooks slice before it — only moved what could be lifted out mechanically, with zero behavior risk, ahead of a real TS/Vite toolchain existing to enforce the `ui → state → core/schemas` dependency direction (§2) automatically — Phase 4's `state/` stores are still the real target.
5. **Phase 4 — introduce `state/`** properly, replacing the `useState` soup with the store modules, one store at a time (`layoutStore` first, since it's the one everything else reads).
6. **Phase 5 — build `extensions/`** for the Marketplace, once `core/`+`schemas/` are stable enough to be a trustworthy target for third-party transforms to validate against.

Each phase should leave `main` deployable. Roadmap features can start landing as soon as their home directory exists — they don't need to wait for the full migration to finish.

**A UX pass, outside this phase numbering** (it's a usability improvement, not a migration step) landed once the third Phase-3 slice above finished: canvas selection used to run only one way (click a key -> the inspector shows it), with no way to go the other direction (hover a combo/behavior in the sidebar -> see where it's used on the keyboard) or to jump from a key straight to the combo/behavior it's already part of. `core/usage.js` gained `findBehaviorUsageKeys` (returns key indices, not just a count, for one layer) to drive a new hover-highlight; `App` gained a small `combosContainingSelectedKey` memo and a `findBehaviorCategory`/`openBehaviorEditor` pair to drive, respectively, a "Part of combo — Edit" chip and a per-slot "Edit this behavior" link; and `InspectorPanel`'s five-tab switcher was redesigned from icon-only buttons into a labeled icon-above-label-below picker. See README.md's own "UX pass" section for the full breakdown file-by-file — it's deliberately not folded into the Phase 3 paragraph above, since nothing here changed *where* code lives, only what it does.
