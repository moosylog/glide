# GLIDE

Graphical Layout & Intent Definition Editor — a visual ZMK keymap editor for MoErgo Glove80/Go60.

## Running it

The modularized `glide.html` (this repo's copy — see "Status" below) needs to be *served*, not opened directly as a `file://` URL: it loads `ui/*.js` as external `type="text/babel"` scripts, and Babel Standalone's in-browser transformer fetches those over XMLHttpRequest to transform their JSX before running them — a fetch browsers refuse for a `file://` document ("Access to XMLHttpRequest ... blocked by CORS policy: ... origin 'null'"), so the whole UI silently fails to load. Serve the directory with any static file server:

```bash
npx serve .
# or
python3 -m http.server
```

then open the URL it prints, instead of double-clicking `glide.html`.

**If you want a single file you can just double-click** (save it locally, email it, keep it on a USB stick, no server involved) — `npm run build:bundle` inlines every local `core/*.js`/`ui/*.js` script and the stylesheet straight into the HTML and writes the result to `dist/glide.html`. That file has zero same-directory dependencies (only the three unpkg.com CDN `<script>` tags stay external, which load fine from `file://` since they're ordinary absolute-URL `<script defer>` GETs, not XHR-fetched-then-transformed) — copy it anywhere and open it directly. Regenerate it after pulling changes with `npm run build:bundle` again; it's a build output (`dist/`), not something to hand-edit or commit changes to.

There is one small build step needed when *changing* GLIDE, not running it: `core/styles/tailwind.generated.css` is a committed, generated file (see `core/styles/README.md`) — regenerate it with `npm run build:css` after adding a Tailwind utility class anywhere in `glide.html`.

## Status: mid-modularization

This repo is partway through the migration described in [`ARCHITECTURE.md`](./ARCHITECTURE.md). **Phase 1 is done**: every pure ZMK domain function (binding parse/synthesis, garbage collection, layer-index reindexing, keycode formatting, geometry) has been extracted out of the single inline script into `core/`, as plain classic scripts that attach their exports to `window.GlideCore`. `glide.html` still contains the React UI (components, state, event handlers) and pulls everything it needs from `core/` via one destructuring line near the top of its script block.

This was a pure extraction, not a rewrite — behavior was verified identical to the pre-extraction monolith across both real sample layouts before and after, covering every interaction in `tests/` (see below).

**A first slice of Phase 3's UI decomposition (see `ARCHITECTURE.md` §7) has also landed early**, the same "pure extraction, not a rewrite" move as Phase 1 above, applied to the UI half of `glide.html` instead of the domain-logic half: every component/helper that was already self-contained enough to lift out — no dependency on `App`'s own ~30 `useState` hooks or handlers, just props and `window.GlideCore` — now lives in `ui/*.js` rather than inside the single 2,600+-line `<script type="text/babel">` block, following the exact same `window.GlideCore`-style pattern (each file is an IIFE that destructures what it needs and attaches its exports to `window.GlideUI`), loaded via ordered `<script>`/`<script type="text/babel" src="...">` tags with zero new build step:

```
ui/
  shared.js       # plain JS (no JSX): keycap palette data/search, getBeautifulLabel/getContrastColor
  canvas.js       # MiniKeyboardMap, KeyComponent, KeyboardContainer (the zoomable/pannable canvas)
  sharedForms.js  # DynamicBehaviorForm, FlowParamForm, ConfirmDialog
  modals.js       # TouchpadSettingsModal, CapabilitiesModal
  builders.js     # the five Behavior Library builder modals (Macro/StickyKey/ModMorph/HoldTap/TapDance)
```

`App` itself — state, handlers, and the JSX that's genuinely specific to it (the canvas/inspector/sidebar layout, the per-key editor) — was deliberately untouched by that first slice; splitting it apart is the harder, deliberate Phase 3 project `ARCHITECTURE.md` describes (custom hooks, then real component boundaries), not something to do accidentally as a side effect of a component lift. `tests/ui/testAppHarness.js` mirrors `glide.html`'s own loading order exactly (`ui/hooks.js`/`ui/shared.js` as plain classic scripts, the four JSX files Babel-compiled in dependency order, then the now-much-smaller main app script), so no test needed to change to prove this — same "verified identical, not just asserted" bar as Phase 1: still 314/314 passing before and after.

**A second slice — the "custom hooks" half of Phase 3 — has now also landed**, applied to the one piece of App's ~30-`useState` "state soup" that was both the most duplicated-in-spirit and the most physically scattered: `config`/undo/redo/dirty-tracking, and the five `localStorage`-backed settings (theme, layout mode, sidebar side, OS override, the Layers/Combos panel's saved width). `ui/hooks.js` (also plain JS, loaded as a classic script right alongside `ui/shared.js`) adds two hooks to the same `window.GlideUI` namespace Stage 1 introduced:

- `useUndoHistory()` — `config`/`setConfig`, `undoStack`/`redoStack`, `isDirty`/`setIsDirty` (plus its `beforeunload` warning and browser-tab-title effect), and `pushHistory`/`undo`/`redo`. Before this, those pieces were declared roughly 250-400 lines apart from each other inside `App` (the state itself near the top, `pushHistory`/`undo`/`redo` much further down, once every earlier handler they don't depend on had already been declared) — genuinely harder to hold in view together than the logic warrants, given `pushHistory` alone is called from around 50 different handlers throughout the file. Every one of those call sites is completely unchanged: they still just call `pushHistory(newConfig)` or read `config`/`isDirty`, now sourced from one `const { config, setConfig, ... } = useUndoHistory();` line near the top of `App` instead of scattered top-level declarations.
- `usePersistedState(key, default, { parse, onChange })` — a generic `localStorage`-backed `useState`, replacing five near-identical "lazy-init from `localStorage`, write-effect on change" pairs with one call each (`onChange` covers theme's extra `document.documentElement.className` side effect; `parse` covers the one setting, panel width, that needs numeric parsing rather than a plain string).

This is a smaller, more surgical move than Stage 1's component extraction — it only touches the specific state clusters above, not `App`'s other ~25 `useState` hooks or its JSX — deliberately: the goal was proving the "hook lifted out, call sites unchanged" pattern works cleanly on GLIDE's actual state shape before doing it more broadly, not a full `state/` rewrite (that's still Phase 4's job, once a real store can enforce `ui → state → core/schemas` at build time). `tests/ui/testAppHarness.js` loads `ui/hooks.js` the same way it loads `ui/shared.js` (a plain classic script, before the Babel-compiled UI files); still 314/314 passing before and after.

**Stage 3 — splitting `App`'s own JSX — has started, deliberately least-coupled-first.** Stage 1 and 2 lifted things *out* of `App` that were already self-contained; `App`'s ~880-line `return (...)` itself (top bar, left sidebar, Settings modal, the key inspector panel — the canvas and the seven behavior/settings modals are already `<KeyboardContainer/>`/`<TouchpadSettingsModal/>`/etc. calls from Stage 1) was still one tree. Splitting *that* apart safely means going in order of how much state a region shares with the rest of `App`, not tackling it all in one pass, and re-running the full 314-test suite after every single extraction rather than batching several before testing. First cut, the least coupled of the four planned pieces: `SettingsModal` (`ui/modals.js`, alongside the other two modals Stage 1 already put there) — GLIDE's theme/key-editor-location/panel-side/target-OS preferences, every one of them already a `usePersistedState` pair from Stage 2, so the component is purely presentational: it reads/writes whatever value+setter prop `App` hands it and owns no state of its own. `detectOs` (used by both `App`'s `effectiveOs` and this modal's "Auto-Detect (WIN)" option label) moved from a top-level helper in `glide.html`'s script to `ui/shared.js`, since it's now genuinely needed from two independently-loaded files rather than one. Second cut: `TopBar` (`ui/topBar.js`) — the persistent header (file identity/unsaved dot, New/Import/Export, Undo/Redo, Settings/Flows Automations). Also purely presentational: every value and handler (`config`, `undo`/`redo`/`undoStack`/`redoStack`, `handleExport`, `showNewMenu`/`setShowNewMenu`, etc.) comes in as a prop, JSX moved verbatim; the `showNewMenu` state declaration itself stayed a plain `useState` in `App` alongside its ~25 remaining ones rather than becoming its own hook, since this step is specifically about the JSX split, not further hook extraction (that's Stage 2's job, applied earlier to the two clusters worth generalizing) — `App` still owns it, `TopBar` just reads/writes it through props. Third cut, the biggest so far: `Sidebar` (`ui/sidebar.js`) — the `<aside>` listing and managing Layers, Combos, and the five Behavior Library editors (Macros/StickyKeys/ModMorphs/HoldTaps/TapDances), around 70 props (every value/handler it touches, including the six `filtered*` search-memo results computed in `App`). Still purely presentational — no new state, no new hooks — but the sheer prop count is real evidence this piece was doing a lot in one place; splitting it further (e.g. one sub-component per Behavior Library list) is a reasonable future move but wasn't necessary just to get it out of `App`'s `return`. `BEHAVIOR_LIBRARY_NAV_MODES` moved to a local constant inside `ui/sidebar.js` itself (nothing else in `App` ever read it, unlike `detectOs` in the first cut, so no new `window.GlideUI` export was needed for it). **Fourth and final cut, the biggest and hardest: `InspectorPanel` (`ui/inspector.js`)** — the per-key/per-combo `<aside>` that opens beside the canvas, holding Combo Gear Settings and the five-tab vertical switcher (Keymap / Advanced Behaviors / Switch Layer / Lighting / JSON) with every tab's full editor, roughly 50 props. Unlike the earlier three cuts, this one didn't stay purely presentational at the call site: the outer `config && (...)` gate that used to wrap `<aside>` at `App`'s call site now sits *inside* `InspectorPanel`'s own return instead, so it can be invoked unconditionally, exactly like `<TopBar/>` and `<Sidebar/>` already are — a small deviation from strict copy-paste, made because the original code gated the *whole* aside on `config`, not just its inner content the way the header/sidebar do. Five small helpers/constants that only this JSX ever read (`SLOT_LABELS`, `SLOT_LINK_LABELS`, `MOD_BASES`, `getModSymbol`, `paletteLabel`) became local constants inside `ui/inspector.js`, matching the `BEHAVIOR_LIBRARY_NAV_MODES` precedent; `KEY_COLOR_PRESETS`, needed both here and by `App`'s own `usedLayoutColors` memo, moved to `ui/shared.js` instead, matching the `detectOs` precedent. Rather than the file-group split floated as a possibility earlier, the panel landed as one cohesive component: its tabs share too much (`renderSlot`, `parsedSlots`, `assignAction`, `isItemActive`, and friends all cross tab boundaries) for a five-file split to be a real simplification rather than just more prop-threading between siblings. With this landed, Stage 3's planned four-step sequence is complete — `App`'s `return` is down to its outer shell (`TopBar`, `Sidebar`, the canvas `<section>`, `InspectorPanel`, and the modals) plus the hooks and handlers every tab still needs.

## UX pass: bidirectional canvas selection + a picker-style inspector switcher

Separate from the modularization stages above — a usability pass, not a refactor — prompted by one long-standing gap: selection only ever ran one way, canvas click -> inspector. Nothing on the sidebar's Combos/Behavior Library lists pointed back at the keyboard, and a key that already belonged to a combo or a named custom behavior had no way to jump to that definition. Five pieces landed together:

1. **Reverse highlight, hover-driven.** `core/usage.js` gained `findBehaviorUsageKeys(config, layerIdx, behaviorName)` alongside the existing `countBehaviorUsage` — same walk, but returning which key indices on one specific layer reference a behavior name, not just a count. `App` tracks `hoveredBehaviorName`/`hoveredComboIdx` (set/cleared by `onMouseEnter`/`onMouseLeave` on every combo row and every Macro/StickyKey/ModMorph/HoldTap/TapDance row in `ui/sidebar.js`) and turns whichever is set into `usageHighlightKeys`, a prop threaded through `KeyboardContainer` into `KeyComponent` (`ui/canvas.js`) as a new `isUsageHighlighted` flag. It renders as its own pulsing amber-glow CSS animation (`.usage-highlight`, in `glide.html`'s `<style>` block) — deliberately never the same look as `.selected`/`.combo-selected`'s orange fill/border, so "this is what you're hovering over elsewhere" can never be mistaken for "this is what's currently selected/being edited."
2. **"Part of combo — Edit" chip.** A key selected outside combo-edit mode that already belongs to one or more combos (checked via a new `combosContainingSelectedKey` memo in `App`, matching each combo's `keyPositions`/`key_positions` against the selected key) now shows a small chip per combo in `InspectorPanel`'s header. Clicking a chip — and only clicking it, never selecting the key itself — calls the same `setEditingComboIdx` the sidebar's own Combos list already used, so it's the exact same jump-into-Zen-Mode path, just reachable from the canvas side too.
3. **Key -> named behavior "Edit" link.** `App` gained `findBehaviorCategory`/`openBehaviorEditor`, a small lookup that checks which of the five Behavior Library arrays (`macros`/`stickyKeys`/`modMorphs`/`holdTaps`/`tapDances`) actually contains an entry with a given custom behavior's name (plain array search, not GLIDE's own naming-convention helpers — those only recognize GLIDE-generated hold-tap/mod-morph/tap-dance names, and a macro or sticky key is normally hand-named). `renderSlot`'s already-filled-slot row now shows a small ✎ button next to the existing "Detach & Customize" one whenever a slot's binding resolves to a real Behavior Library entry, opening that exact behavior's own builder modal via the same `setMacroModalName`/etc. setters the sidebar already used.
4. **The inspector's tab switcher, redesigned.** The five-tab vertical/horizontal switcher inside `InspectorPanel` (Keymap / Advanced Behaviors / Switch Layer / Lighting / JSON) was icon-only with a hover tooltip as its only label — not very discoverable. It's now a labeled picker, icon-above-label-below in every tab (an iOS tab-bar layout, in both of the switcher's orientations — a horizontal strip when the inspector docks on the right, a vertical strip when it docks at the bottom), with a smooth per-button transition into the existing `btn-active` look on activation rather than a flat class swap. No tab was renamed — that naming-collision cleanup (`Advanced Behaviors` vs. the sidebar's `Behavior Library`; `Switch Layer` vs. the sidebar's `Layers`) already happened in an earlier pass; this is purely a legibility upgrade on top of it. A literal shared sliding-pill indicator (measuring each button's position to animate a single element between them) was considered and deliberately skipped — the five labels aren't equal width, especially "Switch Layer", and it wasn't worth the added complexity for a tab switcher.
5. **Tests**: `tests/ui/reverseHighlight.test.js` (hover-highlight for both a combo and a layer-scoped macro), `tests/ui/comboEditChip.test.js` (chip appears/doesn't, selecting a key never auto-enters Zen Mode, clicking the chip does), `tests/ui/behaviorEditLink.test.js` (the ✎ button opens the right builder modal, and is absent for a plain non-custom binding) — plus a new `hoverOn`/`hoverOff` pair in `tests/ui/testAppHarness.js` (dispatches the native `mouseover`/`mouseout` events React's `onMouseEnter`/`onMouseLeave` are actually built on, since jsdom has no real `mouseenter`/`mouseleave`). `tests/ui/behaviorLibraryNav.test.js`'s "no visible text" assertion on the inspector's Advanced Behaviors tab was updated to match its new visible label rather than deleted, since the underlying thing it protects — that tab and the sidebar's "Behavior Library" toggle can't be confused by a text-based lookup — still holds. 321/321 passing.
6. **Real-browser visual QA, after the fact.** The 321 jsdom tests above never render `glide.html` as an actual page — they mount `App` directly with `window.React` pre-set — so a follow-up pass loaded the real file in headless Chromium (proxying the three unpkg CDN `<script>` tags to local copies for the sandbox's outbound-network allowlist; no change to the shipped file) and screenshotted the whole new flow end to end. It caught two real bugs neither the test suite nor a code read had surfaced:
   - `ui/hooks.js` is a plain, non-`defer`, non-Babel `<script>`, so it runs synchronously as soon as the parser reaches it — before the `defer`red React/ReactDOM/Babel tags in `<head>` have executed (deferred scripts always run after parsing finishes, regardless of tag order). Its top-level `const { useState, useEffect, useCallback } = React;` therefore threw against an undefined `React` on every real page load, silently failing to register `useUndoHistory`/`usePersistedState` on `window.GlideUI` and crashing `App` on mount (`useUndoHistory is not a function`) — invisible to jsdom because `testAppHarness.js` sets `window.React` up front, sidestepping real script-loading order entirely. Fixed by moving each hook's `React` destructure inside its own function body, where it only runs once React has actually loaded.
   - `renderSlot`'s already-filled-slot row (`glide.html`) had `flex-1 truncate` without the `min-w-0` every other `flex-1 truncate` span in the codebase already carries (a standard Tailwind-in-flexbox gotcha — `truncate` can't shrink a flex item below its content width without it). Latent before this pass; the new ✎ "Edit this behavior's own definition" button pushed the row from 3 to 4 fixed-width icons and tipped it over into visibly unreadable — the custom-behavior name rendered as a single clipped, overlapping glyph. Fixed both the missing `min-w-0` and, since even a correctly truncating span had almost no room left after the label, "Custom" badge and four icon buttons, by dropping the redundant name text for custom-behavior rows entirely (the "Custom" badge's tooltip and the ✎ button already cover it) rather than just papering over the symptom.

   Everything else — the amber reverse-highlight glow, the combo chip, the forward-link modal, and the tab picker in both its vertical (bottom-docked) and horizontal (right-docked) orientations — rendered as designed with no further changes needed. 321/321 still passing after both fixes.

   Since jsdom structurally can't catch this class of bug, that one-off QA pass turned into a permanent, minimal test: `tests/e2e/smoke.spec.js`, run via `npm run test:e2e` (Playwright Test, config in `playwright.config.js`). It loads the real `glide.html` from a small static server (`tests/e2e/serve.mjs`), stubs the three unpkg CDN requests to local `node_modules` copies (`tests/e2e/cdnStub.js` — glide.html itself still says unpkg.com; only the test's browser session is redirected, same trick the throwaway QA script used), imports the `tynstar.json` fixture, and asserts the app actually mounted and stayed console-error-free. It's deliberately narrow — one test, checking boot health, not behavior (that's still jsdom's job) — and it does catch exactly the bug above: reintroducing `ui/hooks.js`'s original top-level `React` destructure makes it fail immediately, on the first assertion. Wired into CI (`.github/workflows/ci.yml`) after `npm test`. First-time setup on a machine without a cached Chromium build: `npx playwright install chromium`.
7. **A follow-up touch-parity regression, found by checking this pass against Mobile readiness Phase 1's own precedent (below), not by a phone-width layout audit.** Phase 1 already fixed one class of bug — hover-only controls (a layer's clone/rename/delete buttons) being completely unreachable on a touchscreen, which has no hover state — by showing them whenever their row is otherwise active. This later UX pass's reverse-highlight (point 1 above) added a brand new hover-only interaction — `onMouseEnter`/`onMouseLeave` on every combo and Behavior Library row — without carrying that fix forward, so on touch it was 100% inert, not just degraded: nothing else in the app has a mouse-only feature with no touch story at all. Fixed by adding `onPointerDown`/`onPointerUp`/`onPointerCancel` to the same six rows, gated to `e.pointerType !== 'mouse'` (the exact idiom `ui/canvas.js` already uses elsewhere) rather than native `TouchEvent` handlers, which would've been a second, parallel touch code path alongside the Pointer-Events-only approach the rest of the app deliberately standardized on. The result is "press and hold to preview" on touch/pen — not a true hover, since touch has none, but no longer nothing. Proven two ways: two new jsdom cases in `tests/ui/reverseHighlight.test.js` (a touch `pointerdown` previews the highlight and `pointerup` clears it; a mouse `pointerdown` does *not* trigger this path, since mouse already gets the real hover), and, since this bug's whole nature is "only exists once you leave jsdom," a one-off real-browser check with Playwright's `devices['iPhone 13']` profile and genuine dispatched `pointerType: 'touch'` events — confirmed the highlight engages on press and clears on release, zero console errors.

   Deliberately not attempted here: a phone-width *reflow* of the fixed sidebar-plus-canvas desktop chrome. That's Phase 1's own explicitly stated scope boundary ("usable on a tablet or phone but not yet laid out for one... Phase 2, if there's real demand for it") — a design decision, not a bug, and out of scope for a QA/regression pass.

**Schema-driven behavior settings** (`core/behaviors/`): hold-tap and tap-dance settings panels are no longer hand-built JSX per property — `glide.html`'s `DynamicBehaviorForm` component renders a behavior's whole settings panel (labels, widgets, min/max, advanced-property accordion) purely from its entry in `core/behaviors/schemas.js`. Adding or tuning a property (a new field, a different slider range, a new enum option) is now a data change in that one file, not a JSX change. Deliberately plain JS objects rather than TOML or JSON-on-disk: GLIDE has no build step, so a schema format needing its own parser would either add a runtime dependency for no real benefit or force a toolchain migration bundled invisibly into this feature — plain JS objects load exactly like every other `core/*.js` module and stay testable with Vitest, no DOM or build step required. `mod_morph` is registered in the schema for consistency (so tooling can enumerate all three behavior types) but keeps its hand-built per-case mod-toggle panel, since its real editable surface — a list of mod-combination cases, each with its own binding — isn't a flat property list.

**Abstracted file IO** (`core/io/`): loading and exporting a layout used to be one function each in `glide.html`, mixing JSON parsing, shape assumptions, DOM (`FileReader`, anchor-click downloads), and React state updates together. That's now split: `core/io/layoutSchema.js` + `loadLayout.js` are pure functions — `parseLayoutJson(text)` / `loadLayoutObject(obj)` return `{ config, errors }`, validating the fields GLIDE's own logic actually depends on (`layers`, and the optional `holdTaps`/`tapDances`/`modMorphs`/`combos`/`macros`/`layer_names`/`keyboard`) while leaving every other field (MoErgo's `uuid`, `custom_devicetree`, `config_parameters`, `inputListeners`, `stickyKeys`, …) completely untouched — this is deliberately *not* a strict allowlist, since reconstructing the object from known fields would silently drop real user data on every load/export round-trip. `exportLayout.js`'s `serializeLayout`/`getExportFilename` are the export-side equivalent. `glide.html`'s `handleFileUpload`, `fetchTemplate`, and `handleExport` are now thin adapters over these — they get bytes from a `<input type=file>`, a `fetch()`, or an anchor-click download, and hand them to the same pure functions a future API-backed load/save path would call too. Swapping in a backend later means writing a new adapter, not touching validation or serialization logic.

**Flows Automations** (`core/capabilities/`, opened from the toolbar's package-icon button — never a left-nav tab, see below): a browse-and-apply catalog of layout mutators, each one a curated port of a real package from [moosylog/flows4json](https://github.com/moosylog/flows4json). Internally these are still called "Flows" in the code (`core/capabilities/*.js`'s naming, matching their origin repo); to an end user they're presented as **Flows Automations** — a one-shot jq mutation you run against your layout, like a filter, not something you install or manage a lifecycle for (confirmed with the project owner: no uninstall, no persisted state beyond the last run's result). The catalog ships **inside GLIDE** as `core/capabilities/builtinCatalog.js` — a verified array of entries, not a live fetch. It's sourced from the flows4json **repo's own** `catalog.json` (`github.com/moosylog/flows4json`), not the smaller one served from `moosylog.github.io` — the two differ (the live site lags the repo), and the repo is the ground truth: it lists 38 entries, and this file carries **every real mutator in it (32)**, plus one GLIDE-original addition (`hrm_bil60`, a Go60 port of `hrm_bil80` built on direct user request — see below), each individually run with the real jq-web engine against a real layout before being added (`tests/core/capabilities.test.js`'s `builtinCatalog` suite re-verifies every one of them on every test run, so a future jq-web upgrade or GLIDE change that breaks one fails loudly instead of silently). Six are deliberately left out, not scope-trimmed: five launcher cards (`colors_launch_kiilix`, `l_cleaner`, `l_hrm_tuner`, `l_oryx_swap`, `l_qwerty_swap` — no script, just a link to a third-party site; GLIDE never executes an external app on the user's behalf, see below) and `hrm_bil_dynamic` ("Bilateral HRM Sunaku"), which upstream's own `catalog.json` files under a `category` of `"Test"` and — confirmed by actually trying to run it — has a `script` that's truncated mid-expression and fails to even compile; that reads as an unfinished publish on the upstream side, not something to guess-and-patch here. (Upstream's catalog.json also has a real duplicate-uid bug — two entries both literally named `se_symbol`, one Windows/Linux, one macOS — disambiguated here as `se_symbol` / `se_symbol_mac`.) `hrm_bil60` ("Go60 Bilateral HRM") is the one entry in the catalog that isn't from upstream at all: `hrm_bil80` (Sunaku's Bilateral HRM) hardcodes a full literal snapshot of a stock 80-key Glove80 QWERTY layout for its new layers, and Go60 has no F-row and ~20 fewer keys with no verified "default Go60 QWERTY" to transplant that snapshot onto — `hrm_bil60` replicates the same per-finger-layer algorithm on a freshly-built, documented stock Go60 QWERTY base layer instead, using the already-proven Go60 home-row/bilateral-trigger positions from `hrm_add.flows`. The pipeline (`applyFlow.js`) mirrors `core/io`'s pattern exactly: `buildScriptWithParams` prepends `<value> as $<id> |` lines for each declared param (copied byte-for-byte from Flows4JSON's own `getScriptWithParams`, so an automation behaves identically in either app), the script is then run behind a **normalizer prologue** copied verbatim from Flows4JSON's own app (its `index.html`'s FileReader.onload handler) — some real automations (the whole Home-Row Mods family) read a `.layout.keys` positional structure that MoErgo's real export JSON never has; without this prologue they fail with jq's own unhelpful "Cannot iterate over null (null)", even though they work in the real app. `jqRunner.js` runs the assembled script through the real [jq-web](https://www.npmjs.com/package/jq-web) engine, and the result is validated through the *existing* `loadLayoutObject` before it's ever applied — a buggy automation can't hand back a corrupted config, it just fails with a toast and a readable result box. `glide.html`'s Apply button then reuses the *existing* `pushHistory` (free undo/redo) and `runGC`. **Keyboard filtering happens before the modal ever sees the catalog**, not by graying out cards: `glide.html` filters the full bundled catalog down to only the automations compatible with the currently-loaded keyboard (`isFlowCompatible`, `manifest.keyboards`) once per config change, so a Go60 owner never sees a Glove80-only card (or vice versa) in any category, count, or search result — a category with zero automations for the loaded keyboard just doesn't appear. Two entries are scoped to `glove80`-only despite upstream advertising both keyboards for them: `colors_createRGBscheme` and `mirror_keyboard_halves` both hard-code an exact-60-keys check in their real scripts, which collides with GLIDE's own 62-position Go60 geometry model (`core/geometry/go60.js`) — documented in `builtinCatalog.js`'s header rather than shipped silently broken. Six entries (the "Symbols 2 &lt;language&gt;" family — `de_symbol`, `fr_symbol`, `gb_symbol`, `mac_gb_symbol`, `se_symbol`, `se_symbol_mac`) have a real, upstream-documented ordering dependency: each needs a layer literally named `"Symbol"` to already exist, which is what `add_symbl_lyr` creates — not a bug, just a "run this one first" relationship, same as upstream's own docs say. GLIDE never executes an external app on the user's behalf: launcher-only catalog entries (empty `script`, an `appUrl` instead) are dropped entirely at `catalogSchema.js`'s parse boundary, not just hidden in the UI — moot for the bundled catalog (none of the curated entries are launchers) but still enforced structurally. Two verified real-world jq-web 0.5.1 quirks worth knowing: it mis-tokenizes CRLF line endings inside a script (a bare, undetailed compile error — `jqRunner.js` normalizes this defensively before every run) and it strips one leading `"WORD: " ` segment from `error(...)` messages — nothing to fix, just something to expect when reading an error.

**The result box and `successMessage`.** The `.flows` format has no field for "what to do now that this ran" — GLIDE added one, `successMessage`, hand-written per bundled entry from that automation's own description (never invented from the title alone; see `builtinCatalog.js`'s header). `catalogSchema.js` normalizes it through, `applyFlow.js` returns it only when the run actually succeeded (an author's follow-up text would be misleading attached to a validation failure), and `CapabilitiesModal` shows it — success or the real jq error — in a small result box right in that automation's own detail view, replacing the earlier "Recent Activity" log. That's a closer match to what was asked for (a per-automation result, not a running feed) and keeps the cryptic parts of jq's own error output ("Cannot iterate over null (null)") from only flashing in a 2.2s toast.

**Why a modal, not a third left-nav tab.** This first shipped as a tab beside Layers/Combos; feedback from actually using it was that this misrepresented what it is. Layers and Combos are editing *modes* — places spent the whole session flipping between while building a keymap. An automation is an occasional, one-shot action ("run this against my layout, then get out of the way"), closer in kind to Export than to Combos. It opens as a modal from a toolbar button (`CapabilitiesModal` in `glide.html`, titled "Flows Automations").

**Why an app-store-style category grid, not a flat list.** With a growing catalog, a single scrollable list of automations became hard to scan — the ask was specifically for something "app store like." The modal's top-level "home" screen is a grid of category tiles: an icon, a small preview strip of that category's own automation icons, its name, and a count; picking one drills into that category's own list, then into an automation's detail view. Typing in the search box skips both levels of navigation and matches across every category at once, since a known automation's name is faster to type than to browse for. Every list row and detail view also carries a short hardware badge ("Go60 · Glove80", "Go60 only", …) so keyboard compatibility is visible while browsing, not just as a warning after drilling all the way in.

**Startup performance.** GLIDE used to load, for every visitor, with zero loading feedback while React/ReactDOM's *development* builds, Babel Standalone, the Tailwind CDN's in-browser JIT compiler, and the jq-web wasm engine all downloaded and (for Tailwind) recompiled at runtime — several separate network round-trips, blocking, before anything painted. Four fixes, none of them a rewrite: (1) a plain-HTML/CSS loading splash (`#glide-splash` in `glide.html`'s `<body>`, no React/Babel dependency since neither has necessarily loaded yet) shows immediately and removes itself once the real UI has actually mounted; (2) the three head `<script>` tags for React/ReactDOM/Babel are now `defer`red, so the browser can parse and paint that splash instead of blocking on three sequential unpkg round-trips before it even reaches `<body>`; (3) React/ReactDOM point at their `production.min.js` builds instead of `development.js` (smaller payload, no extra runtime checks a shipped app doesn't need); (4) the Tailwind CDN's runtime JIT compiler is gone entirely, replaced by a static, pre-generated stylesheet (`core/styles/tailwind.generated.css` — see that folder's README for how to regenerate it), and jq-web's wasm binary is no longer loaded upfront for every visitor — `glide.html`'s `ensureJqEngineLoaded` injects that one `<script src>` itself, lazily, the first time Flows Automations is actually opened, with a "Loading automation engine…" state on the Apply button in the meantime (`jqEngineStatus` in `CapabilitiesModal`).

**File handling: New/Import/Export, and not losing work by accident.** Once a layout was loaded, there used to be no visible way back to load a *different* one or start blank — the empty-state "Load File"/template buttons only existed before a layout was loaded, and the only path back to them was an unlabeled click on the sidebar's "GLIDE" logo, firing a native `window.confirm("...Unsaved changes will be lost.")` with no way to save first. Since there was also no autosave, "unsaved changes" was *always* true. First fixed with a File menu hidden behind a single icon button in a floating toolbar pill — an improvement over nothing, but real feedback on that version (see "Top bar" below) was that hiding New/Import/Export behind one icon, and putting the unsaved-changes dot inside the Layers/Combos sidebar, wasn't good UX. The current version: New (a small "Start blank" dropdown for Glove80/Go60), Import, and Export are three separate, always-labeled buttons/controls in the top bar, visible the entire time a layout is loaded — no icon-only menu to discover; a real `isDirty` flag (set on every edit that goes through `pushHistory`/`undo`/`redo`, cleared by an actual Export or a fresh load) driving both a small dot next to the layout's name in the top bar and a "• " prefix on the browser tab's title, so the unsaved state is visible even in a background tab; a `beforeunload` handler that actually warns before closing/refreshing a dirty tab; and every action that would discard a dirty layout (Import or New) routing through `guardUnsavedChanges`, which offers **Export First** as a real third option, not just discard-or-cancel.

**`ConfirmDialog`, replacing every native `window.confirm()` in the app.** A browser-native `confirm()` popup reads as an OS-level interruption, not something GLIDE itself is asking, and can't offer more than yes/no. All four call sites that used one (detaching a shared custom behavior, deleting a layer, "Clear All Actions", and the file-discard guard above) now go through one small in-app dialog (`ConfirmDialog` in `glide.html`) and a Promise-based `askConfirm(opts)` helper on `App`, resolving `'confirm' | 'export' | 'cancel'` — a plain yes/no call site just checks `=== 'confirm'`, the same shape as the `if (!window.confirm(...)) return;` guard it replaced.

**Top bar, and where UI elements live.** Direct feedback on the first file-handling pass (above) was that a floating pill of icon buttons over the canvas, plus an unsaved-changes dot sitting inside the Layers/Combos sidebar's own header, competed with the content GLIDE is actually meant to show — not what a tool aiming to be the easiest, most intuitive keyboard-layout editor around should look like. Grounded in real UX guidance rather than guesswork (Nielsen Norman Group's consistency/menu-design heuristics; the common real-world pattern of keeping file-identity chrome — name, dirty state — in a title bar rather than inside a content panel, as apps from GitHub's Primer "Saving" pattern to countless native editors do) and a follow-up decision from the project owner, GLIDE now has a persistent, full-width `<header>` above everything else: the GLIDE mark, the current layout's name, and the unsaved-changes dot sit on the left; New/Import/Export and Undo/Redo/Settings/Flows Automations sit on the right, all only once a layout is loaded. The Layers/Combos sidebar's own header is gone entirely — it's now purely an editing surface (the Layers/Combos tab switcher is the first thing in it), with no file-level chrome mixed in. The floating pills that remain over the canvas (the Zen-Mode/clipboard/hint pill top-center, the zoom controls bottom-right) are deliberately left there: they're contextual to the canvas itself, not file-level actions, so moving them into the header would separate them from the thing they describe.

On the broader "can I move any panel anywhere" question: GLIDE offers **curated layout presets**, not freeform dockable panels. Full drag-anywhere docking (VS Code, Blender, Figma) is a professional/power-user pattern that trades a real learning curve for maximum flexibility — the wrong trade for a tool aimed at being approachable to non-technical keyboard owners first. Consumer tools with a similar audience (Canva, Notion, Google Docs) instead fix the chrome layout and offer a couple of named view *modes*. GLIDE already had one such preset (`layoutMode`: the key inspector as a **Bottom Pane** or a **Right Sidebar**, Settings → "Key Editor Location") and now has a second, matching one for the other panel: `sidebarSide` (**Left**/**Right**, Settings → "Layers/Combos Panel Side"), persisted to `localStorage` exactly like the first. Implemented as a CSS `order` swap on the same two flex children (the sidebar `<aside>` and `<main>`), with the resize-handle side and drag-resize direction mirrored to match — not a rewrite of either panel, just where it sits.

**Touchpad Settings — Go60's two Cirque trackpads (key positions 60/61, the round keys) get a real settings editor.** These used to be a dead click: `isTouchpad` short-circuited `onSelect`/`onContextMenu`/drag entirely, with nothing rendered inside them. Inspired by MoErgo's own touchpad configuration screen (not copied pixel-for-pixel — matched to GLIDE's own visual language instead, e.g. the left-rail-plus-detail-pane layout mirrors the Layers list's own look), clicking a touchpad now opens `TouchpadSettingsModal`: Movement/Scroll mode, a sensitivity multiplier/divisor (a slider for the common case, exact number inputs alongside it so an existing fractional ratio like `11/12` in a real file is never silently rounded away), flip-horizontal/flip-vertical/swap-axes, a Mouse Click target picker (Left/Right/Middle/Button #4/Button #5), a temporary-layer toggle, and the same "Default plus per-layer override" list MoErgo's own editor uses (matching how the underlying ZMK config is actually shaped — one base chain, optional per-layer override nodes).

Underneath, `core/zmk/inputProcessors.js` is a pure parse/build module for the actual ZMK input-processor chain (`&zip_xy_scaler`, `&zip_xy_transform`, `&zip_xy_to_scroll_mapper`, `&zip_click_to_<target>_mapper`, `&zip_temp_layer` — grounded against ZMK's own docs, not guessed), following the same "parse into a friendly model, build back into the exact JSON" shape as `core/behaviors/compile.js`. Two things matter here specifically because this is firmware configuration, not cosmetic UI state: nothing recognized is ever silently dropped — an unfamiliar processor in a chain, or an unfamiliar transform flag, is preserved in `extra`/`extraFlags` and re-emitted unchanged even though the UI doesn't expose it; and this corner of the layout format is encoded differently from an ordinary key binding (`{ code, params: [plain values] }`, not `{ value, params: [{ value }] }`) — confirmed against real MoErgo Go60 exports (`tests/fixtures/go60-touchpads.json`, `go60-touchpads-clickmap.json`) rather than assumed from the binding format used everywhere else in the file. "Disable" is GLIDE's own explicit, reversible convention (a `&zip_xy_scaler 0 1` entry) rather than a guess at an undocumented MoErgo-specific field.

The five Mouse Click targets follow a MoErgo naming pattern — `&zip_click_to_right_click_mapper` and `&zip_click_to_button_4_click_mapper` are confirmed against real exports; `&zip_click_to_middle_click_mapper` and `&zip_click_to_button_5_click_mapper` follow the same pattern but aren't independently confirmed yet, and the UI marks those two with a small `†` and a tooltip saying so. Still deliberately out of scope: an "Action" tab mapping a touchpad click to an arbitrary keyboard behavior (`&kp`, `&mo`, etc.) rather than another mouse button — ZMK's Code Mapper processor (which all of the above build on) only remaps one input-event code to another, so whatever mechanism MoErgo's own "Action" tab uses isn't this, and I don't have a verified real-world example of it yet.

**Mobile readiness, Phase 1 — GLIDE now actually receives touch input; it doesn't yet have a mobile-optimized *layout*.** Every drag-style interaction was mouse-event-only or, for layer reordering, built on the native HTML5 Drag and Drop API — which iOS Safari simply never fires for a finger at all. All of it is now driven by [Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events) instead, one code path for mouse/touch/pen: canvas panning, a key's drag-to-swap, the two sidebar panel resize handles, and layer reordering (native `draggable`/`onDragStart`/`onDragOver`/`onDrop` removed entirely in favor of the same elementFromPoint-hit-testing approach the key-swap drag already used, now triggered from the row's own `∷` grab handle so it doesn't fight with tapping the layer name or its action buttons). Touch has no right-click, so a **long-press** (500ms, cancelled if the finger moves more than the drag threshold first) opens the same context menu a right-click does — implemented in the same pointerdown listener as the drag-to-swap logic so the two can cleanly cancel each other, rather than as a second, separate gesture recognizer racing it. `touch-action: none` and `-webkit-touch-callout: none` on the canvas and keys stop iOS's own press-and-hold text-selection callout and the page's native scroll/pinch from hijacking these gestures.

Two more mobile-specific fixes: `getExportFilename`'s `handleExport` used a `data:` URI anchor download, which mobile Safari (and some Android WebViews) is known to just navigate to/preview instead of actually saving — replaced with a `Blob`/`URL.createObjectURL` object URL (the combination mobile browsers actually honor `download` for), with the old `data:` approach kept as a same-function fallback if `Blob`/`createObjectURL` throws for any reason. And the app's two full-height root containers used Tailwind's `h-screen` (`100vh`), which on mobile Safari is measured *including* the address-bar area — switched to `h-dvh` (`100dvh`, the dynamic viewport height unit), so the layout doesn't get clipped or leave a dead gap as the browser chrome shows/hides during scroll.

Also fixed in passing, not strictly a touch-input issue but found while working through the same interaction code: two "hover to reveal" icon-button rows (a layer's clone/rename/delete buttons, a combo's delete button) were `opacity-0 group-hover:opacity-100` with no other way to reach them — meaning on a touchscreen, which has no hover state at all, those controls were completely unreachable, not just harder to tap. Both now also show at full opacity when their row is the active/selected one, so tapping the row (which touch can already do) reveals its actions.

Deliberately still out of scope for this pass (Phase 2, if there's real demand for it): the fixed sidebar-plus-canvas desktop chrome doesn't reflow into a stacked or drawer-based layout for narrow/phone-width viewports yet, so GLIDE is now *usable* on a tablet or phone but not yet laid out *for* one; and pinch-to-zoom/two-finger-pan on the canvas (currently zoom is buttons-only) wasn't added, since the existing zoom controls already work fine with a tap.

**Macro Builder — GLIDE can now create and edit ZMK macros, not just assign existing ones to a key.** Previously the only macro-related UI anywhere in GLIDE was the ordinary key-assignment palette listing already-defined macro names by name; there was no way to write a new one or see/change what an existing one actually does. A third left-nav tab, **Macros**, sits alongside Layers/Combos: a searchable list of the layout's macros (name, description, step count), with Create/Clone/Delete per row, opening `MacroBuilderModal` on click.

Underneath, `core/zmk/macro.js` is a pure parse/build module for `config.macros`, following the same "parse into a friendly step model, build back into the exact JSON" shape as `core/zmk/inputProcessors.js`. Unlike input-processor chains, a macro's `bindings` array already uses the *same* shape as an ordinary key binding (`{ value: '&kp', params: [...] }`) — confirmed against two real MoErgo exports with 91 real macros between them (`tests/fixtures/tynstar.json`, `tests/fixtures/engrammer.json`), so no format-guessing was needed there. What the module does add structure to: the three ambient mode-setters (`&macro_tap`/`&macro_press`/`&macro_release`), `&macro_pause_for_release` (splits a sequence into a press phase and a release phase — real in tynstar's `&msteams_ptt`, a Ctrl+Shift+M press/release toggle), `&macro_wait_time`/`&macro_tap_time`, and the four `&macro_param_<n>to<n>` parameter-forwarding controls (real in engrammer's HRM macros, which forward the invoking key's own param into a nested hold-tap step). Anything else — `&kp`, `&mo`, another macro or custom behavior invoked as a step (real in engrammer: `&mod_tab_chord_v2_TKZ` invokes `&mod_tab_v1_TKZ` as one of its own steps) — is kept as the exact, untouched binding object rather than re-decomposed, so an unfamiliar or not-yet-modeled step still round-trips losslessly. `tapMs`/`waitMs` being *absent* from a macro (meaning "use the device's compiled-in default") is preserved as distinct from an explicit `0` — collapsing that would silently change compiled firmware behavior; the modal shows both as blank-means-default number inputs, not defaulted-to-zero ones.

Renaming or deleting a macro needed a fuller reference scan than `core/usage.js`'s existing `countBehaviorUsage`, which only walks `layers`+`combos` and misses a macro named from a hold-tap's/tap-dance's own `bindings` list or invoked as a step inside a *different* macro. `findMacroReferences` covers all of these; `renameMacro` rewrites every one of them atomically alongside the macro's own name, and `deleteMacro` on a still-referenced macro routes through the same `askConfirm`/`ConfirmDialog` pattern as every other destructive action in GLIDE (never a native `window.confirm()`), naming what still points at it.

The step editor reuses GLIDE's existing key-assignment palette data (`PALETTE_DATA`/`searchAcrossAllPalette`/`ALL_PALETTE_SECTIONS`) for behavior steps — the same familiar key grid, plus one-click `&mo <layer>` buttons and a free-text fallback for any other behavior name — rather than a second, divergent keycode picker. Step order is changed with up/down buttons (not a pointer-drag reorder like the Layers list): a macro's bindings are typically short and linear, so simple reordering controls cover the real editing pattern without the added complexity of a second drag-and-drop implementation.

**Sticky Key Builder — the same "list-only, no editor" gap Macro Builder closed for macros, closed for `&sk` behaviors.** Sticky keys used to be assignable to a key by name (the ordinary key palette listed them, same as macros before), with no way to create one or see/change its settings. A tab, **Sticky**, sits under the Behavior Library section (see below): a searchable list (name, description, a one-line summary of its non-default flags), Create/Clone/Delete per row, opening `StickyKeyBuilderModal` on click. Much smaller than the Macro Builder's surface, since a sticky key has no ordered step sequence — just four flat properties (ZMK docs: zmk.dev/docs/keymaps/behaviors/sticky-key): `releaseAfterMs` (how long it stays active waiting for another keypress; device default 1000ms), `quickRelease` (deactivate on the next press rather than its release — avoids double-capitalizing), `lazy` (delay activation until just before another key is pressed), and `ignoreModifiers` (let another sticky key stack onto this one before it releases, for chaining modifiers). `core/zmk/stickyKey.js` parses/builds `config.stickyKeys` the same "friendly model in, exact JSON out" way as `macro.js`, grounded against the one real sticky key across both real fixtures (`tests/fixtures/engrammer.json`'s `&sticky_key_quickrel_v1_TKZ` — tynstar.json has none) plus ZMK's own docs for the property set. The same absence-vs-explicit-value care as macros' `tapMs`/`waitMs` applies to all four properties here too — a real sticky key missing a key entirely means "use ZMK's own default," not the same thing as writing that default out explicitly, and collapsing the two would change what ships to firmware even though the *effective* behavior often matches. One thing this module's `bindings` field isn't: unlike a macro's `bindings` (binding objects), a sticky key's `bindings` array is a plain array of behavior-name strings (`["&kp"]`, confirmed against the real fixture) declaring what single-param behavior it wraps — kept opaque and editable as a small "Wraps Behavior" text field defaulting to `&kp`, since ZMK allows wrapping something other than `&kp` even though virtually no real file does. Reference-safety (`findStickyKeyReferences`/`renameStickyKey`/`deleteStickyKey`) mirrors the macro module's exactly, including a genuinely real cross-reference this pass turned up while writing its tests: engrammer's own `&sticky_key_quickrel_v1_TKZ` is invoked as a step inside a *different* macro (`&sticky_key_oneshot_v1_TKZ`) — exactly the kind of reference `core/usage.js`'s `countBehaviorUsage` would miss, and exactly why this needed its own fuller scan rather than reusing that one. `modMorph.test.js` proves `core/zmk/modMorph.js` against both real fixtures' 27 real mod-morphs combined: `normalizeModMorphCases` preserves a real single-sided-mods, non-empty-keepMods case (tynstar's `&parsl`) exactly while still forcing case 0 empty regardless of input; `findModMorphReferences`/`renameModMorph`/`deleteModMorph`/`cloneModMorph` are proven against a real mod-morph that's directly key-bound (every one of tynstar's 21 real mod-morphs actually is) and against a mod-morph invoking another mod-morph as a case's own binding.

**Mod-Morph Builder — the same gap closed for `&mod_morph` behaviors, the best-evidenced of the three.** User-authored mod-morphs were in the identical spot macros and sticky keys were: listed by name in the key-assignment palette, no way to create or edit one — and real fixtures have more of them than either: **21 in tynstar, 6 in engrammer**, all real, user-authored (not GLIDE's own `GLIDE_MM_`-generated ones synthesized for a key's Shift Action, which already have a small mods-only toggle panel of their own via the gear-icon settings view). A tab, **Morphs**, sits alongside it under Behavior Library: a searchable list (name, description, a one-line summary of its trigger mods), Create/Clone/Delete per row, opening `ModMorphBuilderModal` on click.

**Hold-Tap Builder and Tap-Dance Builder — the last two named-behavior types, closing out the set.** Both were the same "assignable by name, no editor" gap the other three closed, and both are heavily used in real files: **36 real hold-taps across both fixtures** (engrammer.json alone has 35 — its whole home-row-mods layout is built from them — tynstar.json has 1, `&strong`), while **neither real fixture has a user-authored tap-dance**, so `tapDance.js`/`tapDanceBuilder.test.js` are grounded on the binding-object `bindings` shape `core/slots.js`'s own `buildBindingAndConfig` already synthesizes for GLIDE-generated tap-dances, plus ZMK's docs, rather than a real top-level example. Two tabs, **Hold-Taps** and **Tap-Dances**, sit alongside Macros/Sticky/Morphs under Behavior Library, each with the same searchable-list-plus-Create/Clone/Delete shape, opening `HoldTapBuilderModal`/`TapDanceBuilderModal` on click.

`core/zmk/holdTap.js` deliberately skips a parse/build layer (same call as `modMorph.js` — the real shape is already close to a form model), but the real data settled one thing the docs alone wouldn't have: a hold-tap's `bindings` is a plain 2-element array of behavior-name **strings** (`["&kp", "&HRM_left_index_tap_v1B_TKZ"]`), not binding objects with params — confirmed against every one of the 36 real records, and matching `core/slots.js`'s own `makeHoldTap`. Real records also carry `holdTriggerKeyPositions`, a per-key physical-position allowlist sometimes 40+ entries long, that the builder has no editor for; `updateHoldTap` merges onto the existing record (`{ ...existing, ...managedFields }`) rather than rebuilding it field-by-field, so editing a hold-tap's tapping term can never silently drop its key-position list — a real data-loss trap the fixture surfaced, not a hypothetical one. The modal exposes flavor (`hold-preferred`/`balanced`/`tap-preferred`), tapping-term/quick-tap/require-prior-idle (all ms, device-default-if-blank), hold-trigger-on-release and retro-tap toggles, and the two behavior-name fields as plain text inputs (no params to pick, unlike a mod-morph's binding).

`core/zmk/tapDance.js` follows the same shape ZMK's docs and `core/slots.js` agree on: an ordered `bindings` array of full binding objects (one per tap count, 2+ required — `&kp A` for the first tap, `&kp B` for the second, and so on), plus a single `tappingTermMs`. The modal reuses `ModMorphBindingPicker` for each tap (full palette search, since these ARE binding objects with params) with an Add Tap / per-row remove control that refuses to go below 2.

Both new modules extend the reference-safety scan one bucket further than the three that came before them: `findHoldTapReferences`/`findTapDanceReferences` also check `stickyKeys[].bindings`, a bucket `stickyKey.js`/`modMorph.js` didn't have yet when they were written (a sticky key's single wrapped-behavior name could, structurally, name a hold-tap or tap-dance, even if no real fixture does it today).

**Behavior Library — the five behavior builders moved out of the primary nav.** With five behavior-editor tabs (Macros/Sticky/Morphs/Hold-Taps/Tap-Dances) alongside the two everyday ones (Layers/Combos), the sidebar was mostly tabs for editors most people would rarely open — cluttering the one workflow (remap a key, build a layer) that's actually common. Layers and Combos now stay as the only always-visible tabs; the five behavior builders live under a collapsible **Behavior Library** section beneath them, collapsed by default on every fresh load, and expandable with one click. The section also auto-expands whenever one of its own tabs is already the active view (e.g. if `leftNavMode` was left pointing at `StickyKeys` from before a collapse), so switching away and back never strands the view on a hidden panel. This is purely a navigation change — no data shape, CRUD function, or existing keyboard shortcut moved — so it didn't touch any `core/zmk/*.js` module, only `glide.html`'s sidebar JSX and the handful of UI tests (`macroBuilder.test.js`, `stickyKeyBuilder.test.js`, `modMorphBuilder.test.js`) whose `open*Tab()` helpers now expand the section first if its tabs aren't already visible. It's called **Behavior Library**, not "Advanced Behaviors" — the first name tried — specifically because GLIDE already has an unrelated, pre-existing per-key inspector tab with that exact label (the icon in the key inspector's bottom toolbar, `activeVerticalTab === 'Advanced'`), which searches and *assigns* an existing behavior to the currently selected key. This new section does something different — create/edit the behavior *definitions* themselves — so it needed its own name; `behaviorLibraryNav.test.js` includes a test proving the two never collide.

**Fixed: the canvas zoom +/- buttons (and every other floating button drawn over the canvas) were dead clicks.** This was a pre-existing bug, unrelated to the Behavior Library work above — the report that flagged it just happened to land the same session. `KeyboardContainer`'s `handlePointerDown` calls `e.currentTarget.setPointerCapture(e.pointerId)` on `pointerdown` for anything that isn't a `.p-key` tile, so the canvas can be click-dragged to pan. But the zoom +/- controls, the Paste button, the Clear Clipboard button, and Focus Mode's "Done Editing" button are all real `<button>`s floating inside that same `canvas-container`, so a `pointerdown` on any of them was *also* captured — which makes the browser retarget the matching `pointerup`/`click` to the capturing element instead of the button, so the button's own `onClick` (the thing that actually changes `canvasScale`) never fires. jsdom's `getBoundingClientRect`/pointer-event stubs don't reproduce this retargeting, which is why the existing test suite never caught it; it only showed up under a real browser with real pointer capture. Fixed by excluding any `e.target.closest('button')` from the capture, the same way `.p-key` tiles already were — confirmed with a real Chromium session (not jsdom) that the zoom percentage now moves symmetrically on repeated clicks, and stays frozen if that one line is reverted.

**UX pass on the key editor and the canvas — three fixes from a design review aimed squarely at GLIDE's non-technical audience.** All three came out of the same review as the naming-collision fix above and are grounded in the same "this is a simplified editor for people who don't know ZMK" principle, not just cosmetics:

- **"You can also specify..." link order and size.** The four "also specify an action" links (`SLOT_LINK_LABELS` in `glide.html`) used to list Shift Action first — purely because it was the first of the four slot types built historically, not because it's what a non-technical user is most likely to want. Reordered to hold → double-tap → label → shift: a Hold action (dual-purpose/home-row-mod keys) is the single most common "extra" a real layout uses; a custom text label needs no ZMK knowledge at all; a Shift-conditional output is the most advanced of the four (it's a mod-morph under the hood), so it now comes last instead of first. The same order now applies to `activeSlotKeys` once a slot is actually added, not just the "also add" links. Also bumped from `text-[11.5px]` to `text-[12.5px]` — at the old size it read like a legal disclaimer to skim past, not a real, useful set of features. `keyEditorSlotOrder.test.js` covers both.
- **Renamed the per-key "Layers" tab to "Switch Layer."** Found while looking into the naming-collision report above: the per-key vertical tab that assigns a layer-*switching* action (Momentary/Layer-Tap/Sticky/Toggle/Switch-To) to the selected key was ALSO titled "Layers" — identical to the left sidebar's own "Layers" toggle, which manages/reorders the layers themselves, a completely different job. Exactly the same class of confusion as "Advanced Behaviors" vs. "Behavior Library," just not caught in that pass. Renamed the per-key tab to **Switch Layer**; nothing about what it does changed, only its title attribute. `switchLayerTab.test.js` covers the rename and the absence of the old collision; `layerTap.test.js` updated to use the new title.
- **Renamed the per-key "Keymap" tab to "Pick Key," reordered the vertical tabs, and made the raw JSON editor read-only by default.** Three small consumer-friendliness changes requested directly: (1) "Keymap" collided with ZMK's own use of that term for the whole config file, when the tab itself only picks one key's basic tap action — renamed to **Pick Key** (its internal `activeVerticalTab` key stays `'Keymap'`, only the label/title changed, so this is a pure rename with nothing else to update). (2) The five vertical tabs are now ordered **Pick Key → Switch Layer → Advanced Behaviors → Lighting → JSON**, putting the two most-used actions first. (3) The JSON tab's `<textarea>` now opens `readOnly` by default (a lock icon toggles `jsonUnlocked`, resetting back to locked any time the selected key or combo changes), so a stray keystroke can't silently corrupt a key's binding; the **Apply JSON** button only appears once unlocked, and a "Read-only — click the lock to edit" hint shows while it's locked. `jsonTabLockAndTabOrder.test.js` (new, 6 tests) covers the tab order, the rename, the read-only default (no Apply button, unlock hint shown), unlocking/re-locking via the icon, and the auto-relock on key switch.
- **Lighting: Paint Mode, and key selection no longer bounces the panel back to Keymap.** Two compounding problems made coloring more than one key tedious: (1) `handleCanvasKeySelect` unconditionally forced `activeVerticalTab` back to `'Keymap'` every time a different key was clicked on the canvas — so picking a color on the Lighting tab, then clicking the next key to color, silently kicked you back to Keymap, forcing a re-click of Lighting for every single key; (2) even once that stopped, coloring was still strictly one key at a time (select, then click a swatch). Fixed both: `handleCanvasKeySelect` no longer force-switches tabs at all — whichever tab is open when you select a different key stays open, which equally helps Advanced Behaviors and Switch Layer (assign the same behavior/layer action to several keys in a row without re-opening the tab each time), not just Lighting. And Lighting gained an actual **Paint Mode** toggle: pick a color (arms `paintColor`, shown with a ring on the armed swatch, including the "off" swatch arming the eraser), turn Paint Mode on, then click or click-drag across keys directly on the canvas to color them — no per-key select-then-swatch-click round trip. A whole drag stroke lands as **one** undo step, not one per key touched: `applyPaintColorToKey` writes straight into `config` during the drag (bypassing `pushHistory` entirely) while `paintStrokeBaseRef` holds the config snapshot from just before the stroke started, and `commitPaintStroke` (fired on `pointerup`/`pointercancel`) is what turns that one snapshot into the stroke's single history entry and runs the same `runGC` pass every other edit already goes through. Paint Mode's canvas effect is gated on `activeVerticalTab === 'Lighting'` (`paintMode && activeVerticalTab === 'Lighting'`), so switching tabs stops it immediately even though the toggle itself stays visually "on" until turned off. `paintMode.test.js` covers arming, the disabled-until-armed toggle state, single-click paint, multi-key drag paint as one undo step, and the tab-switch cutoff; it also proves the sticky-tab fix for Lighting, Switch Layer, and Advanced Behaviors.

- **A unified "What do you want to do?" command palette, plus a real search bug it surfaced.** GLIDE's own pitch copy ("Whether your goal is 'I want Home-Row Mods', 'I want to double-tap this key for a symbol'...") promises that you describe what you want and GLIDE finds it — but before this, that was only true if you already knew which of three separate places to look: the Flows Automations modal for a pre-built automation, a per-key inspector slot for a double-tap/hold/label action, or the Advanced Behaviors builders for something you'd already created. Added a new `CommandPaletteModal` (`ui/modals.js`), opened from a new "What do you want to do?" button in the top bar (`ui/topBar.js`, between Export and Undo/Redo) or via `glide.html`'s new `showCommandPalette`/`paletteSearchText` state, that searches all three at once: the Flows catalog (title/subtitle/category/description), the layout's own already-created macros/sticky-keys/mod-morphs/hold-taps/tap-dances (name/description), and a small fixed list of "how do I…" tips for things that aren't a catalog entry at all (double-tap, shift-action, hold-action, swapping two keys by drag, custom key labels, right-click). Clicking a Flow result opens the *existing* Flows modal straight to that flow's own detail view (`openFlowFromPalette` — no duplicate apply logic); clicking a behavior opens its real builder modal via the same `openBehaviorEditor` the inspector's own "✎ Edit this behavior's own definition" button uses. While building this, also fixed the Flows modal's own pre-existing search to match a flow's `description`, not just its title/subtitle/category (it was missing hits like "letters" for Home-Row Mods, whose title/subtitle/category never mention that word). Verifying the new palette in a real browser then surfaced a real, previously-unnoticed bug in *both* search sites: the catalog's own text is hyphenated throughout ("Home-Row Mods", "home-row keys"), but nobody types it that way — searching "home row mods" (or the pitch copy's own exact phrase) came up completely empty, because a plain substring match never folds the hyphen. Fixed with a shared `normalizeForSearch` helper (folds `-`/`_` to spaces, collapses whitespace, lowercases) applied to both the palette and the pre-existing Flows modal search. `tests/ui/commandPalette.test.js` (new, 7 tests) covers opening/closing and clearing search, a Flow result routing into the real Flows modal, a behavior result opening its real builder, the hyphen-normalization fix in both directions, a "how do I" tip matching on a full natural-language phrase, and the empty/no-match guidance states; `tests/ui/capabilitiesModal.test.js` gained 2 more tests for the description-match and hyphen-normalization fixes on the pre-existing search. Re-verified visually in a real Playwright/Chromium session: "home row" now surfaces "Home-Row Mods" (plus its two related entries), and clicking through from the palette correctly lands on the Flows modal's own detail view.

Structurally the smallest of the three new core modules, `core/zmk/modMorph.js`, by design: a mod-morph always has exactly two cases (ZMK docs: zmk.dev/docs/keymaps/behaviors/mod-morph — `&mod_morph` has exactly one `mods` bitmask to test, not an arbitrary list), so the module skips the parse/build translation layer macro.js and stickyKey.js both have — the real JSON shape (`{ name, description, cases: [{ binding, mods, keepMods }, ...] }`) is already the friendly model a settings UI wants, one-to-one. What it does add is the same CRUD/reference-safety layer as the other two (`findModMorphReferences`/`renameModMorph`/`deleteModMorph`/`cloneModMorph`/`uniqueModMorphName`), copied structurally since a mod-morph's name can be referenced from exactly the same places. `normalizeModMorphCases` enforces the one real invariant found in every real example across both fixtures: case 0 (the default) always has empty `mods`/`keepMods` — that's not a UI choice, it's inherent to what "default" means for a single-bitmask behavior. The modal's two binding pickers reuse the exact same palette Change/search UI the Macro Builder's step editor uses; the trigger-mods and keep-mods grids are the full 8-flag set (`MOD_LSFT`/`MOD_RSFT`/`MOD_LCTL`/`MOD_RCTL`/`MOD_LALT`/`MOD_RALT`/`MOD_LGUI`/`MOD_RGUI`), grounded against real fixture variety that isn't just "both shifts": tynstar's `&parsl`/`&parsr` each trigger on only *one* side's Shift and also set a non-empty `keepMods`, so both a single-sided trigger and a non-default keep-mods value needed to actually work, not just the common both-shift/no-keep-mods case.

`tests/ui/touchInteractions.test.js` proves the touch path specifically (not just that the old mouse path still works under a different event name) by dispatching real `PointerEvent`s with `pointerType: 'touch'`: a touch drag from one key to another swaps their bindings; a plain tap with no movement just selects the key; holding a touch pointer past the long-press threshold opens the context menu, and moving first cancels the long-press and starts a drag instead; a mouse pointer never triggers the long-press path at all; and dragging a layer's grab handle onto another layer's row reorders the layer list. Since jsdom has no layout engine, `document.elementFromPoint` (used for hit-testing which key/layer a pointer is currently over) is stubbed per-test via a new `stubElementFromPoint` test-harness helper.

Why classic scripts instead of real ES module `import`/`export`: `glide.html`'s UI script still runs through Babel Standalone's in-browser JSX transform (`<script type="text/babel">`), which evaluates as a classic script, not a module — mixing that with real `import` statements would need an import map or a bundler, which is exactly what Phase 4 (Vite) introduces. For now, `core/*.js` files are loaded as ordinary `<script src>` tags (in dependency order) before the babel script, each wrapped in an IIFE that reads its dependencies off `window.GlideCore` and adds its own exports to it — the same shape real ES modules will take once a build step exists, just without the syntax yet.
