# GLIDE

Graphical Layout & Intent Definition Editor — a visual ZMK keymap editor for MoErgo Glove80/Go60.

## Running it

No build step to *run* GLIDE — open `glide.html` directly in a browser, or serve the directory with any static file server (needed for the `core/*.js` `<script src>` tags to load over `file://`-restricted browsers):

```bash
npx serve .
# or
python3 -m http.server
```

There is one small build step, but it's only needed when *changing* GLIDE, not running it: `core/styles/tailwind.generated.css` is a committed, generated file (see `core/styles/README.md`) — regenerate it with `npm run build:css` after adding a Tailwind utility class anywhere in `glide.html`.

## Status: mid-modularization

This repo is partway through the migration described in [`ARCHITECTURE.md`](./ARCHITECTURE.md). **Phase 1 is done**: every pure ZMK domain function (binding parse/synthesis, garbage collection, layer-index reindexing, keycode formatting, geometry) has been extracted out of the single inline script into `core/`, as plain classic scripts that attach their exports to `window.GlideCore`. `glide.html` still contains the React UI (components, state, event handlers) and pulls everything it needs from `core/` via one destructuring line near the top of its script block.

This was a pure extraction, not a rewrite — behavior was verified identical to the pre-extraction monolith across both real sample layouts before and after, covering every interaction in `tests/` (see below).

```
glide.html              # UI: React components, state, handlers — everything NOT in core/
core/
  zmk/
    naming.js           # GLIDE_ht_/mm_/td_ naming convention + ownership description
    layerPointers.js    # LAYER_POINTER_BEHAVIORS
  keycodes/
    zmkMap.js           # keycode -> display symbol tables
    modChain.js         # modifier-wrapped keycode compose/decompose
  geometry/
    convertGeo.js        # shared geometry math
    glove80.js / go60.js # per-board raw geometry + key-position names
  gc.js                  # runGC — behavior garbage collection
  usage.js                # countBehaviorUsage, isGlideNativeBindingValue
  slots.js                # the tap/hold/shiftTap/doubleTap <-> binding engine
  describe.js             # human-readable binding/keycode formatting
  layerShift.js           # layer-index reindexing on insert/delete/move
  behaviors/
    schemas.js             # declarative hold_tap/tap_dance/mod_morph property schemas
    registry.js            # getBehaviorSchema / getAllBehaviorSchemas / getDefaultValues
    compile.js              # coerces raw widget input against a schema (clamp/validate/default)
  io/
    layoutSchema.js         # declarative shape of a layout JSON + validateLayout()
    loadLayout.js           # parseLayoutJson / loadLayoutObject — pure parse+validate, no DOM
    exportLayout.js         # serializeLayout / getExportFilename — pure serialize, no DOM
  capabilities/
    paramBinding.js         # buildScriptWithParams — Flows4JSON's own param->jq-variable binding
    catalogSchema.js        # parseCatalog / isFlowCompatible — catalog validation; drops launcher/appUrl cards
    jqRunner.js             # runJqScript — thin async wrapper over the global jq-web engine, normalizes CRLF
    applyFlow.js            # applyFlow — .layout.keys normalizer prologue -> bind params -> run jq -> validate
```

**Schema-driven behavior settings** (`core/behaviors/`): hold-tap and tap-dance settings panels are no longer hand-built JSX per property — `glide.html`'s `DynamicBehaviorForm` component renders a behavior's whole settings panel (labels, widgets, min/max, advanced-property accordion) purely from its entry in `core/behaviors/schemas.js`. Adding or tuning a property (a new field, a different slider range, a new enum option) is now a data change in that one file, not a JSX change. Deliberately plain JS objects rather than TOML or JSON-on-disk: GLIDE has no build step, so a schema format needing its own parser would either add a runtime dependency for no real benefit or force a toolchain migration bundled invisibly into this feature — plain JS objects load exactly like every other `core/*.js` module and stay testable with Vitest, no DOM or build step required. `mod_morph` is registered in the schema for consistency (so tooling can enumerate all three behavior types) but keeps its hand-built per-case mod-toggle panel, since its real editable surface — a list of mod-combination cases, each with its own binding — isn't a flat property list.

**Abstracted file IO** (`core/io/`): loading and exporting a layout used to be one function each in `glide.html`, mixing JSON parsing, shape assumptions, DOM (`FileReader`, anchor-click downloads), and React state updates together. That's now split: `core/io/layoutSchema.js` + `loadLayout.js` are pure functions — `parseLayoutJson(text)` / `loadLayoutObject(obj)` return `{ config, errors }`, validating the fields GLIDE's own logic actually depends on (`layers`, and the optional `holdTaps`/`tapDances`/`modMorphs`/`combos`/`macros`/`layer_names`/`keyboard`) while leaving every other field (MoErgo's `uuid`, `custom_devicetree`, `config_parameters`, `inputListeners`, `stickyKeys`, …) completely untouched — this is deliberately *not* a strict allowlist, since reconstructing the object from known fields would silently drop real user data on every load/export round-trip. `exportLayout.js`'s `serializeLayout`/`getExportFilename` are the export-side equivalent. `glide.html`'s `handleFileUpload`, `fetchTemplate`, and `handleExport` are now thin adapters over these — they get bytes from a `<input type=file>`, a `fetch()`, or an anchor-click download, and hand them to the same pure functions a future API-backed load/save path would call too. Swapping in a backend later means writing a new adapter, not touching validation or serialization logic.

**Flows Automations** (`core/capabilities/`, opened from the toolbar's package-icon button — never a left-nav tab, see below): a browse-and-apply catalog of layout mutators, each one a curated port of a real package from [moosylog/flows4json](https://github.com/moosylog/flows4json). Internally these are still called "Flows" in the code (`core/capabilities/*.js`'s naming, matching their origin repo); to an end user they're presented as **Flows Automations** — a one-shot jq mutation you run against your layout, like a filter, not something you install or manage a lifecycle for (confirmed with the project owner: no uninstall, no persisted state beyond the last run's result). The catalog ships **inside GLIDE** as `core/capabilities/builtinCatalog.js` — a verified array of entries, not a live fetch. It's sourced from the flows4json **repo's own** `catalog.json` (`github.com/moosylog/flows4json`), not the smaller one served from `moosylog.github.io` — the two differ (the live site lags the repo), and the repo is the ground truth: it lists 38 entries, and this file carries **every real mutator in it (32)**, each individually run with the real jq-web engine against a real layout before being added (`tests/core/capabilities.test.js`'s `builtinCatalog` suite re-verifies every one of them on every test run, so a future jq-web upgrade or GLIDE change that breaks one fails loudly instead of silently). Six are deliberately left out, not scope-trimmed: five launcher cards (`colors_launch_kiilix`, `l_cleaner`, `l_hrm_tuner`, `l_oryx_swap`, `l_qwerty_swap` — no script, just a link to a third-party site; GLIDE never executes an external app on the user's behalf, see below) and `hrm_bil_dynamic` ("Bilateral HRM Sunaku"), which upstream's own `catalog.json` files under a `category` of `"Test"` and — confirmed by actually trying to run it — has a `script` that's truncated mid-expression and fails to even compile; that reads as an unfinished publish on the upstream side, not something to guess-and-patch here. (Upstream's catalog.json also has a real duplicate-uid bug — two entries both literally named `se_symbol`, one Windows/Linux, one macOS — disambiguated here as `se_symbol` / `se_symbol_mac`.) The pipeline (`applyFlow.js`) mirrors `core/io`'s pattern exactly: `buildScriptWithParams` prepends `<value> as $<id> |` lines for each declared param (copied byte-for-byte from Flows4JSON's own `getScriptWithParams`, so an automation behaves identically in either app), the script is then run behind a **normalizer prologue** copied verbatim from Flows4JSON's own app (its `index.html`'s FileReader.onload handler) — some real automations (the whole Home-Row Mods family) read a `.layout.keys` positional structure that MoErgo's real export JSON never has; without this prologue they fail with jq's own unhelpful "Cannot iterate over null (null)", even though they work in the real app. `jqRunner.js` runs the assembled script through the real [jq-web](https://www.npmjs.com/package/jq-web) engine, and the result is validated through the *existing* `loadLayoutObject` before it's ever applied — a buggy automation can't hand back a corrupted config, it just fails with a toast and a readable result box. `glide.html`'s Apply button then reuses the *existing* `pushHistory` (free undo/redo) and `runGC`. **Keyboard filtering happens before the modal ever sees the catalog**, not by graying out cards: `glide.html` filters the full bundled catalog down to only the automations compatible with the currently-loaded keyboard (`isFlowCompatible`, `manifest.keyboards`) once per config change, so a Go60 owner never sees a Glove80-only card (or vice versa) in any category, count, or search result — a category with zero automations for the loaded keyboard just doesn't appear. Two entries are scoped to `glove80`-only despite upstream advertising both keyboards for them: `colors_createRGBscheme` and `mirror_keyboard_halves` both hard-code an exact-60-keys check in their real scripts, which collides with GLIDE's own 62-position Go60 geometry model (`core/geometry/go60.js`) — documented in `builtinCatalog.js`'s header rather than shipped silently broken. Six entries (the "Symbols 2 &lt;language&gt;" family — `de_symbol`, `fr_symbol`, `gb_symbol`, `mac_gb_symbol`, `se_symbol`, `se_symbol_mac`) have a real, upstream-documented ordering dependency: each needs a layer literally named `"Symbol"` to already exist, which is what `add_symbl_lyr` creates — not a bug, just a "run this one first" relationship, same as upstream's own docs say. GLIDE never executes an external app on the user's behalf: launcher-only catalog entries (empty `script`, an `appUrl` instead) are dropped entirely at `catalogSchema.js`'s parse boundary, not just hidden in the UI — moot for the bundled catalog (none of the curated entries are launchers) but still enforced structurally. Two verified real-world jq-web 0.5.1 quirks worth knowing: it mis-tokenizes CRLF line endings inside a script (a bare, undetailed compile error — `jqRunner.js` normalizes this defensively before every run) and it strips one leading `"WORD: " ` segment from `error(...)` messages — nothing to fix, just something to expect when reading an error.

**The result box and `successMessage`.** The `.flows` format has no field for "what to do now that this ran" — GLIDE added one, `successMessage`, hand-written per bundled entry from that automation's own description (never invented from the title alone; see `builtinCatalog.js`'s header). `catalogSchema.js` normalizes it through, `applyFlow.js` returns it only when the run actually succeeded (an author's follow-up text would be misleading attached to a validation failure), and `CapabilitiesModal` shows it — success or the real jq error — in a small result box right in that automation's own detail view, replacing the earlier "Recent Activity" log. That's a closer match to what was asked for (a per-automation result, not a running feed) and keeps the cryptic parts of jq's own error output ("Cannot iterate over null (null)") from only flashing in a 2.2s toast.

**Why a modal, not a third left-nav tab.** This first shipped as a tab beside Layers/Combos; feedback from actually using it was that this misrepresented what it is. Layers and Combos are editing *modes* — places spent the whole session flipping between while building a keymap. An automation is an occasional, one-shot action ("run this against my layout, then get out of the way"), closer in kind to Export than to Combos. It opens as a modal from a toolbar button (`CapabilitiesModal` in `glide.html`, titled "Flows Automations").

**Why an app-store-style category grid, not a flat list.** With a growing catalog, a single scrollable list of automations became hard to scan — the ask was specifically for something "app store like." The modal's top-level "home" screen is a grid of category tiles: an icon, a small preview strip of that category's own automation icons, its name, and a count; picking one drills into that category's own list, then into an automation's detail view. Typing in the search box skips both levels of navigation and matches across every category at once, since a known automation's name is faster to type than to browse for. Every list row and detail view also carries a short hardware badge ("Go60 · Glove80", "Go60 only", …) so keyboard compatibility is visible while browsing, not just as a warning after drilling all the way in.

**Startup performance.** GLIDE used to load, for every visitor, with zero loading feedback while React/ReactDOM's *development* builds, Babel Standalone, the Tailwind CDN's in-browser JIT compiler, and the jq-web wasm engine all downloaded and (for Tailwind) recompiled at runtime — several separate network round-trips, blocking, before anything painted. Four fixes, none of them a rewrite: (1) a plain-HTML/CSS loading splash (`#glide-splash` in `glide.html`'s `<body>`, no React/Babel dependency since neither has necessarily loaded yet) shows immediately and removes itself once the real UI has actually mounted; (2) the three head `<script>` tags for React/ReactDOM/Babel are now `defer`red, so the browser can parse and paint that splash instead of blocking on three sequential unpkg round-trips before it even reaches `<body>`; (3) React/ReactDOM point at their `production.min.js` builds instead of `development.js` (smaller payload, no extra runtime checks a shipped app doesn't need); (4) the Tailwind CDN's runtime JIT compiler is gone entirely, replaced by a static, pre-generated stylesheet (`core/styles/tailwind.generated.css` — see that folder's README for how to regenerate it), and jq-web's wasm binary is no longer loaded upfront for every visitor — `glide.html`'s `ensureJqEngineLoaded` injects that one `<script src>` itself, lazily, the first time Flows Automations is actually opened, with a "Loading automation engine…" state on the Apply button in the meantime (`jqEngineStatus` in `CapabilitiesModal`).

**File handling: New/Import/Export, and not losing work by accident.** Once a layout was loaded, there used to be no visible way back to load a *different* one or start blank — the empty-state "Load File"/template buttons only existed before a layout was loaded, and the only path back to them was an unlabeled click on the sidebar's "GLIDE" logo, firing a native `window.confirm("...Unsaved changes will be lost.")` with no way to save first. Since there was also no autosave, "unsaved changes" was *always* true. First fixed with a File menu hidden behind a single icon button in a floating toolbar pill — an improvement over nothing, but real feedback on that version (see "Top bar" below) was that hiding New/Import/Export behind one icon, and putting the unsaved-changes dot inside the Layers/Combos sidebar, wasn't good UX. The current version: New (a small "Start blank" dropdown for Glove80/Go60), Import, and Export are three separate, always-labeled buttons/controls in the top bar, visible the entire time a layout is loaded — no icon-only menu to discover; a real `isDirty` flag (set on every edit that goes through `pushHistory`/`undo`/`redo`, cleared by an actual Export or a fresh load) driving both a small dot next to the layout's name in the top bar and a "• " prefix on the browser tab's title, so the unsaved state is visible even in a background tab; a `beforeunload` handler that actually warns before closing/refreshing a dirty tab; and every action that would discard a dirty layout (Import or New) routing through `guardUnsavedChanges`, which offers **Export First** as a real third option, not just discard-or-cancel.

**`ConfirmDialog`, replacing every native `window.confirm()` in the app.** A browser-native `confirm()` popup reads as an OS-level interruption, not something GLIDE itself is asking, and can't offer more than yes/no. All four call sites that used one (detaching a shared custom behavior, deleting a layer, "Clear All Actions", and the file-discard guard above) now go through one small in-app dialog (`ConfirmDialog` in `glide.html`) and a Promise-based `askConfirm(opts)` helper on `App`, resolving `'confirm' | 'export' | 'cancel'` — a plain yes/no call site just checks `=== 'confirm'`, the same shape as the `if (!window.confirm(...)) return;` guard it replaced.

**Top bar, and where UI elements live.** Direct feedback on the first file-handling pass (above) was that a floating pill of icon buttons over the canvas, plus an unsaved-changes dot sitting inside the Layers/Combos sidebar's own header, competed with the content GLIDE is actually meant to show — not what a tool aiming to be the easiest, most intuitive keyboard-layout editor around should look like. Grounded in real UX guidance rather than guesswork (Nielsen Norman Group's consistency/menu-design heuristics; the common real-world pattern of keeping file-identity chrome — name, dirty state — in a title bar rather than inside a content panel, as apps from GitHub's Primer "Saving" pattern to countless native editors do) and a follow-up decision from the project owner, GLIDE now has a persistent, full-width `<header>` above everything else: the GLIDE mark, the current layout's name, and the unsaved-changes dot sit on the left; New/Import/Export and Undo/Redo/Settings/Flows Automations sit on the right, all only once a layout is loaded. The Layers/Combos sidebar's own header is gone entirely — it's now purely an editing surface (the Layers/Combos tab switcher is the first thing in it), with no file-level chrome mixed in. The floating pills that remain over the canvas (the Zen-Mode/clipboard/hint pill top-center, the zoom controls bottom-right) are deliberately left there: they're contextual to the canvas itself, not file-level actions, so moving them into the header would separate them from the thing they describe.

On the broader "can I move any panel anywhere" question: GLIDE offers **curated layout presets**, not freeform dockable panels. Full drag-anywhere docking (VS Code, Blender, Figma) is a professional/power-user pattern that trades a real learning curve for maximum flexibility — the wrong trade for a tool aimed at being approachable to non-technical keyboard owners first. Consumer tools with a similar audience (Canva, Notion, Google Docs) instead fix the chrome layout and offer a couple of named view *modes*. GLIDE already had one such preset (`layoutMode`: the key inspector as a **Bottom Pane** or a **Right Sidebar**, Settings → "Key Editor Location") and now has a second, matching one for the other panel: `sidebarSide` (**Left**/**Right**, Settings → "Layers/Combos Panel Side"), persisted to `localStorage` exactly like the first. Implemented as a CSS `order` swap on the same two flex children (the sidebar `<aside>` and `<main>`), with the resize-handle side and drag-resize direction mirrored to match — not a rewrite of either panel, just where it sits.

Why classic scripts instead of real ES module `import`/`export`: `glide.html`'s UI script still runs through Babel Standalone's in-browser JSX transform (`<script type="text/babel">`), which evaluates as a classic script, not a module — mixing that with real `import` statements would need an import map or a bundler, which is exactly what Phase 4 (Vite) introduces. For now, `core/*.js` files are loaded as ordinary `<script src>` tags (in dependency order) before the babel script, each wrapped in an IIFE that reads its dependencies off `window.GlideCore` and adds its own exports to it — the same shape real ES modules will take once a build step exists, just without the syntax yet.

## Testing

Two layers of tests, both run by the same `npm test` / CI job:

**`tests/core/*.test.js`** (101 tests, Node environment, no DOM) — every `core/*.js` module, anchored on this session's real bugs rather than starting from generic coverage. `tests/core/slots.test.js` and `layerShift.test.js` are the two worth reading first: each documents the exact broken contract, the fix, and (for the layer-index bug) verifies against the real Engrammer fixture's 7 affected keys with a false-positive check across the whole file. `layerShift.test.js` also covers the `combo.layers: [-1]` ("applies to all layers") sentinel — an invariant that must survive layer insert/delete/move untouched, and which would otherwise collide with `remapVal`'s unrelated internal `-1` ("this reference was deleted") meaning. `behaviorRegistry.test.js` and `behaviorCompile.test.js` cover the schema-driven behavior engine: registered schemas match `core/slots.js`'s real synthesized defaults exactly (not an idealized shape), and the compiler clamps/coerces/falls-back on out-of-range or malformed widget input. `combos.test.js` pins `MAX_COMBO_KEYS` to ZMK's real default. `io.test.js` covers the abstracted file-IO layer: schema validation against both real fixtures and deliberately malformed input, the `{ keymap: {...} }` unwrap, and — critically — that `serializeLayout` round-trips every field of a real fixture unchanged, including ones GLIDE's own logic never reads (`uuid`, `custom_devicetree`, …), proving the validator never silently drops data. `capabilities.test.js` runs the **real jq-web engine** (not a mock) against ten real `.flows` files copied verbatim from `moosylog/flows4json` (`tests/fixtures/flows/`, including `hrm_add.flows` — the real Home-Row Mods automation) — proving actual Flows4JSON packages apply correctly through GLIDE's pipeline, including the `.layout.keys` normalizer prologue, the CRLF-mistokenization and error-message-stripping quirks, and that `applyFlow` rejects hardware-incompatible automations and jq results that fail layout validation before they ever touch app state, and that the synthetic `.layout` scratch space never survives into what GLIDE keeps. Its `builtinCatalog` suite separately proves every one of the 32 entries in the GLIDE-bundled `core/capabilities/builtinCatalog.js` — the actual shipped catalog, using each entry's own embedded script rather than a separate fixture file — parses cleanly, declares a non-empty `successMessage`, runs successfully against a real, compatible layout (pre-running `add_symbl_lyr` first for the six "Symbols 2 …" entries that require its output), and matches the exact set of upstream uids expected (so a launcher card or the broken `hrm_bil_dynamic` entry silently reappearing would fail the suite, not just go unnoticed), plus that `colors_createRGBscheme` and `mirror_keyboard_halves` are both correctly scoped to `glove80`-only.

**`tests/ui/*.test.js`** (13 files, jsdom environment via a `// @vitest-environment jsdom` pragma) — the UI/state-layer bugs `core/` unit tests structurally can't reach, since they never lived in `core/` to begin with:
- `clearAllActions.test.js` — the React state-batching bug where the trash-icon button only cleared the custom label, leaving the real binding untouched.
- `layerTap.test.js` — the empty-key Layer-Tap bug, end to end through real clicks.
- `detachCustomize.test.js` — Detach & Customize cloning a shared behavior without mutating the other key(s) that reference it.
- `comboSearch.test.js` — the Combos list's name/key search and layer filter, verified against the real Engrammer fixture's 21 combos (including the classic React-in-jsdom pitfall of setting an `<input>`'s value directly vs. through the native setter React actually tracks).
- `comboLifecycle.test.js` — the full create → pick keys (Zen mode) → rename → find-by-search → delete flow, against tynstar's fixture.
- `comboLayerScope.test.js` — the "Combo applies on all layers" checkbox and its specific-layer picker: defaults to all-layers on a new combo, the picker can never be left with zero layers selected (falls back to the active layer), and creating/editing a combo always resets the inspector tab back to Keymap. Assertions check against tynstar's real layer names (`Base`, `Meeting`, `Lower`, …), not placeholder `Layer N` labels, since that's what the fixture actually has.
- `dynamicBehaviorForm.test.js` — proves the schema-driven settings panel is actually wired into the real gear/Settings UI (not just that the core-layer schema/compile unit tests pass in isolation): renders `&strong`'s real stored values, edits Tapping Term through the generic `number_input` widget and confirms the schema's max clamps an out-of-range value, and toggles Retro Tap through the generic `toggle` widget.
- `comboConstraints.test.js` — two real ZMK limitations GLIDE's UI used to let you violate: a combo can select at most `MAX_COMBO_KEYS` (4) key positions (blocked with a toast, not silently truncated on export), and editing a combo only ever offers the primary action slot — never shiftTap/hold/doubleTap/label, since ZMK combos fire exactly one binding with no hold-vs-tap distinction at the combo level.
- `fileLoadErrors.test.js` — proves `core/io/loadLayout.js`'s validation is wired into the real upload flow: malformed JSON and a schema violation (missing `layers`) each surface a specific, readable toast instead of crashing or silently failing, and a good file still loads normally afterward.
- `fileMenuAndUnsavedChanges.test.js` — the top bar's New/Import/Export are actually there and functional once a layout is loaded (always-visible labeled controls, not an icon-only menu), not just on the empty start screen; an edit marks the layout dirty (the dot next to the layout name, the browser tab's "• " title prefix); Import/New while dirty pauses behind `ConfirmDialog` rather than silently discarding, Cancel leaves the current layout completely untouched, "Discard & Continue" actually replaces it, and "Export First" really exports (confirmed via jsdom's own navigation-attempt log for the anchor-click download) before doing so.
- `panelSidePreset.test.js` — the Layers/Combos panel-side preset (Settings → "Layers/Combos Panel Side"): defaults to Left, switching to Right actually reorders the panel (via its CSS `order`) and persists the choice to `localStorage`, switching back restores it, and a stored "right" preference is honored on a fresh mount.
- `capabilitiesModal.test.js` — the Flows Automations modal end to end, against the real GLIDE-bundled 32-entry catalog (no fetch mocking — there's no fetch to mock anymore): confirms it's a toolbar-triggered modal, not a left-nav tab; confirms the top-level screen is a category grid over all nine categories (including the two newest, `Mouse Controls` and `Symbols`, each with its own icon), not a flat list, and that search skips straight to matching automations across every category; drills into a category and then an automation's own detail view; applies a param-free real automation (Fn_combos), confirming the real combos it generates land in app state and that a success result box shows its custom `successMessage`; applies the real Home-Row Mods flow and confirms the `.layout.keys` normalizer prevents the "Cannot iterate over null" crash; confirms running an automation twice replaces its result box rather than growing a log; confirms **keyboard filtering happens before the catalog ever reaches the modal**, not by dimming — a glove80-only automation (`colors_createRGBscheme`) never appears in its category or in search results while a Go60 layout is loaded, and vice versa for a go60-only one (`Gaming Layer 60`/`Gaming Layer 80`) on a real Glove80 fixture; applies the real macOS/Windows modifier remapper and the real Alternative Layouts automation (its select param); and confirms the per-row hardware badge ("Go60 only", "Glove80 only", "Go60 · Glove80") is visible while browsing, not just after drilling in. Wires the real jq-web engine to `window.jq` itself, since the test harness doesn't load the production CDN `<script>` tag.

These compile `glide.html`'s script block with the exact same Babel settings its own `<script type="text/babel">` tag uses in-browser (`tests/ui/testAppHarness.js`), then mount it with real React 18 in jsdom — the same approach used to find and prove these three bugs interactively earlier in this project's history, now permanent. (Playwright, per `ARCHITECTURE.md`, is still the plan once Phase 3 introduces a real dev/build environment with browser binaries available; this jsdom approach is the version provable in the meantime, and ports over with minimal changes when that happens.)

`tests/fixtures/` holds the two real sample layouts (tynstar's and Glorious Engrammer v52b) used as golden files throughout both layers, a minimal synthetic Go60 layout (`go60.json`, for automations that check `.keyboard`), and `flows/` — ten real `.flows` files copied verbatim from `moosylog/flows4json`, covering the original entries exercised by `capabilities.test.js`'s detailed jqRunner/applyFlow suite; the rest of the 32-entry bundled catalog is verified straight from its own embedded script in `builtinCatalog.js` (no separate fixture file needed) by that same file's `builtinCatalog` suite.

```bash
npm install
npm test        # single run — everything in tests/
npm run test:watch
```

CI (`.github/workflows/ci.yml`) runs this on every push and PR.
